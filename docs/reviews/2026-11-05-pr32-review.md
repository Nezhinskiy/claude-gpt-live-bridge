# Review of PR #32: Settings lists the sessions still on the old mod

- Pull request: [getLiveBridge/LiveBridge#32](https://github.com/getLiveBridge/LiveBridge/pull/32),
  `feat/mod-version-on-join` → `dev`
- Head reviewed: `b50c6b9` (one commit), base `origin/dev` at `02aa5c5`
- Skills: `superpowers:requesting-code-review`, `simplify` (report only, nothing applied),
  `security-review`
- Verification: `scripts/check.sh` exits 0 on `b50c6b9`: 314 Swift tests in 32 suites and 65 mod
  engine tests pass, and nothing was skipped. The Settings line itself is SwiftUI in the untested
  app target, and it was not tried in a running app.

## Verdict

**Merge after fixes.** It has no Critical findings and 2 Important ones: the `.byHand` state, and
a rejoin that no test covers. The rest are Minor. The security pass found no vulnerabilities.

**Is the design elegant enough?** Mostly yes. Only the mod knows which code it is running, and only
the app knows its own version, so an optional field on the join is the smallest channel that can
answer the question. The field is parsed into `AppVersion` once, at the edge, and the raw string
is dropped. The rule lives in BridgeCore under test. The list stays out of `SessionRow`, which
goes over the wire to every mod that polls. There is one real design gap: whether the list shows
at all is still decided by a `switch` in untested SwiftUI, and that switch hides the list in the
`.byHand` state (Important 1).

**Is anything redundant?** Yes, a little:

- the conditional spread for `modVersion` (S1);
- a second read-and-parse path in the mod (S2);
- a `var` field with a default in a struct of `let`s (S4);
- a second pass over the registry with a dead fallback, copied from `rows()` (S5);
- the app's version parsed twice (S6).

None of them is serious. The module-level `modVersion` looks redundant but is defensible; see
"Considered and declined".

## The checks asked for

| Question | Answer |
|---|---|
| A mod that sends no version | `modVersion` decodes as nil, so the session counts as old and is listed (`SessionRegistry.swift:253`). This is right for a 0.3.0 mod. |
| A mod that sends a version that does not parse | `AppVersion("…")` gives nil, so the session counts as old. This is right for anything except a current mod whose manifest could not be read (Minor R9). |
| Rejoin after `/clear`, a title change or an app restart | The version is kept, by construction: `BridgeLink.join` strips only `replaces` and `owner` into `#joined` (`link.ts:63`), and `follow()` spreads `...joined` (`register.tsx:191`). The registry overwrites the version on every join, including a `replaces` join (`SessionRegistry.swift:101`). No test covers this (Important 2). |
| The listed labels against the registry's labels | The same `labels()` disambiguation as `rows()`, in join order, so the list matches the menu. The code is copied, not shared (S5). |
| Can an attacker-controlled `modVersion` reach the UI unbounded? | No. Only the parsed `AppVersion` is stored: exactly `X.Y.Z`, at most six digits per part. It is only compared, never shown. The UI shows labels, which are titles capped at 80 characters, the same exposure the menu already has. |
| Is the wire change backward compatible both ways? | Yes. An old mod with the new app: the field is optional, and its absence counts as old. A new mod with an old app: `Router.decodeBody` is a plain `JSONDecoder()` (`Router.swift:12`), which ignores keys it does not know. |
| Is the Settings line right in every state of `UpdateRecord.mod`? | No record: nothing is shown, which is right. `.updated` with an empty list: nothing, which is right. `.updated` with names: the list, which is right. `.byHand`: the commands but **no list**, while the README says Settings lists those sessions (Important 1). App version does not parse: no list, and no update record either, because `App.swift:190` requires a parsed version, so the two can never be inconsistent. |

## superpowers:requesting-code-review

### Important

**R1. The `.byHand` state shows no list, but the README says Settings lists those sessions.**

- Where: `app/Sources/LiveBridge/UpdateSection.swift:94-101`, and `README.md:156` with its six
  translations.
- The problem:
  - The list sits inside `case .updated`.
  - In the README, the new sentence ("Settings lists the joined ones that still do") directly
    follows the by-hand commands, so it covers both outcomes. In `.byHand` it claims more than the
    code does, which AGENTS.md forbids ("Docs never claim more than the code enforces").
  - After the owner runs the two commands, the thing they most need is the list of sessions still
    to restart, and Settings shows nothing.
  - The rule "show it only when `.updated`" is also the only rule left in an untested view.
  - The `simplify` altitude angle raised the same point.
- Suggested fix:
  - Move the `older` block out of the `switch`, below it, so it shows in both outcomes. It is true
    in both: before the commands run, every joined session is old; after them, each session drops
    off the list once it restarts.
  - The view then holds no rule beyond "non-empty → show", and the list itself is already tested
    in BridgeCore.
  - If the wording "until restarted" reads wrong in `.byHand`, use one sentence that fits both
    outcomes, such as "Still on the old mod: A, B."

**R2. No mod test covers a rejoin keeping the version, which the change depends on.**

- Where: `plugin/tests/lifecycle.test.tsx:23` (`clearRejoinsWithNewId`) and `:39`
  (`renameRejoins`), with the app-restart path. Only `/live on` is covered:
  `theJoinNamesTheModsVersion` (`lifecycle.test.tsx:267`).
- The problem:
  - `world.modVersion` defaults to `null`, so every existing rejoin test sends no version.
  - A later change to `BridgeLink.join` that strips `modVersion` alongside `replaces` and `owner`
    would pass every test, and so would a change to `follow()` that builds the body afresh.
  - Either regression would list a session as "on the old mod" right after `/clear` or a rename.
    That reproduces the reported symptom: the line stays after a restart.
- Suggested fix: one engine test that sets `world.modVersion = '0.3.1'`, turns on, and then
  triggers `/clear`, a rename and an app restart (a 404 on the next poll). It expects
  `modVersion: '0.3.1'` in every rejoin body. Setting `world.modVersion` in the existing `/clear`
  and rename tests would also do.

### Minor

**R3. Nothing checks that `$.plugin.root` points at the right folder.**

- Where: `plugin/hooks/register.tsx:134` and `plugin/tests/fake-bridge.ts:127`.
- The problem:
  - The fake answers any path that ends in `/.claude-plugin/plugin.json`, so the test passes
    whatever `root` is.
  - The engine's type says `root` is "the plugin's directory (the one holding plugin.json)", which
    could also be read as the `.claude-plugin` folder itself.
  - The engine's own `fs.read` example, `${$.plugin.root}/hooks/weights.bin`, puts `hooks/` under
    the root. So the PR's path is very likely right. The reviewer subagent rated this Important;
    I downgraded it on that evidence.
  - If the path were wrong, every session would be listed forever, which is the original bug with
    names added.
- Suggested fix: make the fake answer only `${root}/.claude-plugin/plugin.json` for the harness's
  actual root, and confirm once with `claude --plugin-dir plugin` that a join carries
  `modVersion`. The PR body says this was not tried.

**R4. A test doc comment was split from its test.**

- Where: `app/Tests/BridgeCoreTests/SessionRegistryTests.swift:228-230`.
- The problem: the new test went in between the comment "`/clear` gives the session a new id…"
  and `joinReplacingAnIdMovesTheSession`. The new test now carries a three-line comment whose
  first line describes another test, and `joinReplacingAnIdMovesTheSession` has lost its comment.
  The `simplify` reuse and simplification angles raised the same point.
- Suggested fix: move the new test and its own two lines above line 228.

**R5. The spec still quotes the sentence this PR removes.**

- Where: `docs/specs/2026-11-02-in-app-update-design.md:37`.
- The problem: the spec still says "Claude Code sessions already open keep the old mod until they
  restart." The documentation policy says "Superseded prose is removed in the same change that
  supersedes it".
- Suggested fix: describe the list there, in both outcomes as R1 proposes.

**R6. An undecided release number is written into the code, and the fixture contradicts it.**

- Where: `app/Sources/BridgeCore/Wire/Wire.swift:81-82`,
  `app/Tests/BridgeCoreTests/SessionRegistryTests.swift:229` and
  `wire/fixtures/join-version.json:2`.
- The problem:
  - The two comments say "a mod before 0.3.1", but the CHANGELOG entry is still under Unreleased
    and says "before this release". If the next release is 0.4.0, both comments become false.
  - The fixture's `"modVersion": "0.3.0"` is a version that never sends this field.
- Suggested fix: write "a mod from before this field", and use `"0.3.1"` (or whatever the release
  will be) in the fixture. Alternatively, settle on 0.3.1 now.

**R7. Some comments describe the rule imprecisely.**

- `SessionRegistry.swift:52` says "nil when it named none", but the field is also nil when the
  version does not parse.
- `Bridge.swift:600` says "on a mod older than the app", but the list also includes mods that name
  no version. Align it with the registry's own doc ("older than `app`, or names no version").
- `plugin/hooks/wire.ts:32-38`: the `JoinBody` doc describes `replaces` and `owner` but not
  `modVersion`. `Wire.swift` documents it, and the two halves of the wire should say the same.

**R8. One test checks two behaviours, and one guard has no test.**

- Where: `SessionRegistryTests.swift:231-240`.
- The problem: the test checks the listing rule (older, current, no version) and also that a later
  join with a newer mod takes the session off the list. AGENTS.md asks for one behaviour per test.
  The `appVersion == nil` guard in `Bridge.current` (`Bridge.swift:110-111`) has no test.
- Suggested fix: split out "a join with a current mod takes the session off the list". Optionally,
  add a `BridgeTests` case where `appVersion: nil` leaves the list empty.

**R9. A current mod that cannot read its manifest is listed as old for good.**

- Where: `plugin/hooks/register.tsx:133-137` and `SessionRegistry.swift:253`.
- The problem: if `ownVersion` fails (a missing, unreadable or non-JSON `plugin.json`), a current
  mod sends no version. Settings then says "On the old mod until restarted" for a session that a
  restart will not fix, and nothing records why.
- Suggested fix: `$.ui.log` the failure in `ownVersion`, so the false entry can be diagnosed. The
  rule "no version counts as old" is right and should stay.

## simplify (four angles: reuse, simplification, efficiency, altitude; report only)

### Minor

**S1. The conditional spread can be a plain field.**

- Where: `plugin/hooks/register.tsx:148`.
- The problem: `...(modVersion && { modVersion })` sends the same bytes as `modVersion` written as
  a plain field, because `#send` uses `JSON.stringify`, which drops `undefined`. It is the only
  reason the line had to wrap.
- Suggested fix: `link?.join({ sessionId, title, modVersion, ...(byOwner && { owner: true }) })`.

**S2. `ownVersion` repeats the read-then-parse step that `readTitle` already has.**

- Where: `plugin/hooks/register.tsx:133-137`; compare `register.tsx:108`.
- The problem: there are now two ways the mod reads a file into JSON:
  `$.fs.read(p).then(t => parseRecord(String(t)), () => null)` in `readTitle`, and
  `.catch(() => null)` plus `String(manifest ?? '')` in `ownVersion`.
- Suggested fix: lift a module-level `readJSON(path)` and use it in both places.

**S3. A `var` and an `if` where the line above uses an `if` expression.**

- Where: `app/Sources/BridgeCore/Bridge.swift:110-111`.
- Suggested fix:
  `let olderMods = if let appVersion { await registry.labelsOnAnOlderMod(than: appVersion) } else { [String]() }`.
  This matches `minutes` on line 108.

**S4. `BridgeUpdate.labelsOnAnOlderMod` is the only `var` with a default in a struct of `let`s.**

- Where: `Bridge.swift:601`.
- The problem: the default exists only so that `MenuTests.swift:70` still compiles.
- Suggested fix: make it `let` and pass `labelsOnAnOlderMod: []` in that one helper.

**S5. `labelsOnAnOlderMod` copies `rows()` and does its work a second time.**

- Where: `SessionRegistry.swift:251-255`; compare `:240-247`.
- The problem:
  - It repeats `ordered()`, `labels()` and the fallback `labels[id] ?? session.title`. That
    fallback can never fire, because `Labels.disambiguate` returns a label for every session.
  - `Bridge.current` already calls `rows()` through `status`, so every `changed()` now runs a
    second sort, a second disambiguation and one more actor hop. `changed()` runs after every
    POST, on the one-second sweep, and on every call event. With a handful of sessions the cost is
    not material.
  - The real cost is that the label rule now lives in two places.
- Suggested fix: a private `label(of:)` that both functions use; or put the version on an internal
  row and filter what `rows()` already built.

**S6. `AppVersion(versionText)` is parsed twice.**

- Where: `app/Sources/LiveBridge/App.swift:160` and `:190`.
- Suggested fix: keep one `appVersion` property next to `versionText` (`App.swift:106`), so both
  readers use the same value.

**S7. `Bridge(appVersion:)` defaults to nil, so most Bridges silently never compute the list.**

- Where: `Bridge.swift:56, 67`.
- The problem: every `BridgeTests` instance built without the argument never computes the list.
  An optional is right at the app's edge, because `versionText` can be `"?"`, but the default
  hides the parameter from every other caller.
- Suggested fix: drop the `= nil` default, so each construction states it.

**S8. The new tests bypass the existing join helpers.**

- Where: `SessionRegistryTests.swift:15` and `BridgeTests.swift:137`.
- The problem: the new tests write `registry.join(JoinBody(...))` out in full because the helpers
  take no version.
- Suggested fix: add `modVersion: String? = nil` to both helpers. Then `join(c, "Gamma")` and the
  others read like the rest of the file.

**S9. The relaunch notification keeps the old fixed sentence.**

- Where: `App.swift:232-234`.
- The problem: the notification still says that open sessions keep the old mod until they
  restart. That is true when it is posted, since no session has rejoined yet. But the same fact
  now has a fixed text in the notification and a live one in Settings.
- Suggested fix: optionally end it with "Settings lists them", as the `.byHand` notice already
  points to Settings.

### Considered and declined

- **Read the version inside `turnOn` instead of a module-level `modVersion` (simplification and
  efficiency angles).**
  - Declined. Reading at `session.start` ties the version to the code that was actually loaded,
    because the hook runs again on every load and reload.
  - A read at a later `/live on` could find a `plugin.json` replaced in place (a `--plugin-dir`
    working tree, or a root that is not per-version) and report a version the running code is
    not.
  - Worth one comment on the variable saying so. The read costs about a millisecond per session
    start.
- **Move the version comparison out of `SessionRegistry` into a presenter type (altitude
  angle).** Declined.
  - The rule is in BridgeCore under test, as AGENTS.md asks.
  - A new type for one sentence is more weight than the rule carries.
  - With R1 fixed, the view holds no rule.

## security-review

**No findings.** Nothing reached the bar of confidence ≥ 8 with a concrete exploit path, so the
false-positive filtering step had nothing to filter. Concerns examined and dismissed:

- **A crafted `modVersion` reaching the UI.** It cannot. Only the parsed `AppVersion` is stored
  (`SessionRegistry.swift:101`), and it is only compared, never rendered.
- **Markdown or format specifiers in titles**, in `Text("On the old mod until restarted: \(…)")`.
  An interpolated `String` in a `LocalizedStringKey` literal is substituted as an argument, not
  parsed as markdown. The titles are already shown verbatim in the menu and are capped at 80
  characters.
- **Bypassing the owner-removal rule.** The removed check in `join` runs before `modVersion` is
  read, and the field has no say in authorisation, targeting or routing.
- **A same-user process faking the version.** It can hide or add a name on a display hint, which
  is far less than what SECURITY.md already accepts from same-user processes: join, become the
  target, or answer handoffs.
- **Path traversal through `$.plugin.root`.** The engine sets the root and nobody else controls
  it. The read is a fixed relative path inside it, and only a string `version` field is used.
- **Deserialisation of `plugin.json`.** It goes through the existing `parseRecord` (`JSON.parse`
  inside a try), and only `.version` is read, with a type check.
- **Data exposure.** `modVersion` is not echoed in any reply. `BridgeUpdate.labelsOnAnOlderMod`
  carries labels the status already shows. The fixture uses `00000000-…` ids and
  `Example session`.

## Considered and set aside

- **Sessions that never joined also keep the old mod.** The app cannot know about them, and the
  README now limits the claim to joined sessions.
- **A title containing `, ` makes the joined list ambiguous.** This is cosmetic.
- **Pre-release mod versions such as `0.3.1-beta` count as old.** Releases are strictly `X.Y.Z`,
  and `check.sh` keeps `plugin.json` and `Info.plist` in lockstep.
- **There is no cap on how many names the list shows.** The menu already has the same exposure,
  and that predates this PR.
