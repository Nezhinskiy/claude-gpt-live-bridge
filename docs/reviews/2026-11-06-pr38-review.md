## Findings

### Important

**P-1. The title and commit subject claim more than the evidence.** PR title and `dfcbf83`: "docs:
require Claude Code 2.1.301, the lowest version the mod runs on".

- The PR body says "the real floor may be lower" and lists 2.1.297 to 2.1.300 as unverified. The
  subject states as fact what the body disclaims. The commit's own body has it right: "the lowest
  installed version that validates, type-checks and passes the mod's tests".
- The PR's only deliverable is a truthful version claim, and `dev` is merged with merge commits, so
  the subject stays in the log and cannot be corrected later. A reader could take it as proof that
  2.1.300 fails. AGENTS.md: docs never claim more than the code enforces.
- **Resolution:** amend before merge, for example `docs: require Claude Code 2.1.301, the lowest
  version verified`, and match the title.

### Minor

**P-2. The `(mods)` gloss now gives a reason the evidence contradicts.** `README.md:83`,
`README.es.md:86`, `README.fr.md:91`, `README.hi.md:85`, `README.ru.md:87`, `README.uk.md:87`,
`README.zh-CN.md:73`.

- It reads as "this version is needed for mods", and zh-CN says it outright: `（支持模组）`,
  "supports mods". But 2.1.296 has mods: it validates a hooks module and rejects this one over one
  rule of its source check.
- **Resolution:** drop the parenthetical in all seven; `site/index.html:136` reads fine without it.

**P-3. "that works" is a little wider than what was checked.** `CHANGELOG.md:36`. A successful model
turn on the real engine and the band in the real terminal are unverified on every version. "checked"
hedges it, and a reader takes "works" as "loads and joins", which is proved, so the harm is small.
**Resolution:** "the lowest version checked that loads the mod", rewrapped.

**P-4. Nothing keeps the new number true.** `.github/workflows/ci.yml:32`.

- CI runs 2.1.309 only, so it never runs the floor, and a later mod change can raise it with no
  failure. That is how 2.1.289 came to be false.
- The engine offers no declaration to lean on: `engines` in `plugin.json` gets "Unknown field …
  Claude Code ignores unrecognized fields" from `plugin validate` on 2.1.312. The owner on an old
  engine gets no message from the mod, because the mod is what failed to load.
- **Resolution:** a follow-up, not in this docs PR: run `plugin validate`, `typecheck` and `plugin
  test` at the floor in a second CI step, so the number has a home that can fail. That also gives
  P-5's fact a place.

**P-5. Why the floor is what it is has no home.** The engine's rule on `$` is a platform finding and
lives only in the PR body, which is not a document. The next person to raise or lower the floor has
to rediscover it. **Resolution:** a short item in ADR 0001 under "Claude Code mod API", with the
table.

1. **Every place agrees.** 15 live statements in 8 files, all 2.1.301: two in each of the seven

3. **The claim against the evidence.** "You need" and "or later" (`README.md:52`, `:83`) state a
   necessity that 2.1.297 to 2.1.300 leave unproved, and "2.1.301 is the lowest version checked" is

   same way. The README does not claim the mod fails below it, nor that a model turn was seen. The
   overclaims are P-1 and, slightly, P-3.
4. **The changelog entry fits.** `### Fixed` is right: the sentence was false and no behaviour
   changed. It is first in the section, sensibly, as the one entry a user may have to act on, in the
   neighbours' voice, and wrapped as they are (98 and 97 columns).
5. **One fact, one home.** `README.md:83` is the home. `README.md:52` and `site/index.html:136` copy
   it beside a link that already says the details are there, as they copy macOS 14 and Swift 6.0, so

   site would cut 15 statements to 7, but for one version only, against the pattern. If wanted, do
   it for all of them, in a separate change.
