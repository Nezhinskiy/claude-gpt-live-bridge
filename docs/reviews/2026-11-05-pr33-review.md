## Is it elegant? Is anything redundant?

**Elegant: yes.** It is the smallest shape the codebase's pattern asks for: one `Command` case,
one footer item in the pure `MenuContent`, one selector in `StatusMenu`'s exhaustive switch, one
URL constant. No new type, state or dependency. The compiler forced the `keyEquivalent` switch to
be updated, so nothing is left half-wired. The URL is derived from `Release.repository`, so the
repository name keeps one home. The handler rightly skips `later {}`: that exists for work that
opens a window or alert past menu tracking, and `copyJoinCommand` and the microphone-settings
open (`MenuRows.swift:68`) do the same without it. The item is a native `NSMenuItem` with a plain
title, so VoiceOver and the system's menu behaviour come free. The README and translation lines
are one clause each, keep the item name in English as the other menu items are kept, and are
accurate. Every place that enumerates the menu was updated (seven READMEs; grep for `Command`,
`.settings` and `Quit LiveBridge` finds nothing else).

**Redundant: only in the tests and two comments.** Nothing in the production code. The ordering
test repeats what three outline tests already pin (R-1), the `ReleaseTests` test re-types the
literal it guards (R-3), and one doc comment names its only consumer (R-2).

## 1. `superpowers:requesting-code-review`

### Minor

- **R-1. `theMenuOffersAStarOnGitHub` is redundant.** `app/Tests/BridgeCoreTests/MenuTests.swift:123-129`.
  The item and its place directly above Settings are already pinned by the two `.outline ==`
  tests the diff edits (lines 110 and 160) and by `withoutABridgeOnlyTheProblemAndTheFooterAreLeft`
  (line 244); a reorder or removal fails all three. The new test's `star! + 1 == settings!` adds
  no failure mode they miss, uses force-unwraps, and its doc comment states the motive ("the
  classic way to support an open-source app") where no sibling test states one.
  Fix: delete the test and its comment; the outline edits are the real test. (Star relative to
  Install is covered by the footer order and needs no new test.)
- **R-2. Loose doc comment on the constant.** `app/Sources/BridgeCore/Update/Release.swift:37`.
  "Its page on GitHub, where the menu's star item goes." ties a model-level constant to one UI
  consumer, and "Its" is vague.
  Fix: `/// The repository's page on GitHub.`
- **R-3. `theRepositoryPageIsTheReleasesRepository` pins a literal against a literal.**
  `app/Tests/BridgeCoreTests/ReleaseTests.swift:72-74`. It re-types the string the production code
  interpolates and only guards against a typo or trailing-slash change in a trivial
  `URL(string:)`. Harmless and defensible; strictly it is the only test touching the constant.
  Fix (optional): keep it, or drop it under "one behaviour, one test". If kept, rename it for the
  behaviour ("the repository page is the repository's GitHub URL").
- **R-4. `README.md:228` is 101 columns.** The surrounding prose wraps at 100.
  Fix: break before "(opens the" so the line ends at "**Star LiveBridge on GitHub**".
- **R-5. `SECURITY.md:248` enumerates the app's own requests** ("two kinds of request, and no
  others"). The claim stays true, since the item asks the default browser to open a page and the
  app makes no request. A privacy-minded reader might still ask; one clause ("**Star LiveBridge
  on GitHub** only opens the repository's page in your browser; the app sends nothing") would
  pre-empt it. Not required; no rule is violated.

Declined to judge (owner's call or out of scope): whether to ship a promotional menu item at all
