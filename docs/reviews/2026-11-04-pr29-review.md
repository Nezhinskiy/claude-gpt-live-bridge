## Answers to the brief's questions

- **Does the code match the spec and the rulings?** Yes, with two exceptions:
  - C1: "code blocks and tables removed" does not hold for a long `[LAST]`.
  - R6: the step text falls back to a stale reply, which the ledger already defers.

  Every Review Focus test exists and can fail, except that `lastDropsCodeAndKeepsTheEnd` never
  meets an odd fence (C1). Some drop paths are tested only below the bridge (R2).
- **The fetch never reaches Claude, keeps the question's route and the handoff's wait apart,
  never counts as unheard.** All hold:
  - The fetch never reaches Claude: `realtimeEvent(.contextFetch)` touches none of `route`,
    `questionRoute`, `awaited`, `record` or `enqueue`.
  - It never counts as unheard: the answer goes only through `.speak`, or through `heldFetch`
    and then `.speak`.
  - The tests `aFetchNeverReachesClaude`, `aFetchKeepsTheQuestionsRoute`,
    `aFetchAndAHandoffKeepTheirOwnWaits` and `aFetchsAnswerIsSpoken` would each fail on a
    regression.
- **Is the fetch dropped on a target change, Stop, a closed line and the session leaving?** Yes:
  - Target change and closed line: `hangUp` clears `fetching`.
  - Stop: `end` resets the whole machine.
  - The session leaving: `followTarget` sends `conversationChanged`, or stops the call when no
    session is left.
  - `/clear`: `join(replaces:)` moves the whole `Session`, `fetchDue` included, and
    `rename` moves `fetching`.

  The registry's left-over `fetchDue` is harmless, because both consumers check
  `machine.fetching`. But the fetch lives in two actors (S1), which lets a narrow race through
  (R3), and the bridge guard that makes it safe is untested (R2).
- **What leaves the Mac.** A local process cannot get a `[LAST]` spoken without a fetch:
  - `[LAST]` is sent only while `registry.endFetch(of:)` and `machine.fetching == id` both hold.
  - `fetching` is set only by the voice's `refresh context` handoff.
  - The line is never stored or seeded.
  - It is flattened (brackets, line breaks) and redacted before it is cut.

  But it is not always "code blocks and tables removed" (C1). SECURITY.md and README Privacy are
  otherwise no stronger than the code. They say the fetch is a model instruction, not a control,
  that injected text can make the voice fetch, and that digits are ignored in the brief.
- **Permission prompts.** Untouched:
  - The mod still has no `tool.check` hook, and `classic.PermissionRequest` is unchanged.
  - In the restructured `AskUserQuestion` hook, `answerQuestion` is still wired only on the
    voice-turn path (`tracker.running !== null && link.session`). A typed turn's question only
    feeds `asking`, which is text for `[LAST]`. The prompt tells the voice that such a question
    waits at the keyboard; that is an instruction, and nothing in the code can answer it.
- **Is the architecture elegant enough? Not yet.** The behaviour is right, and the two hard
  calls are sound:
  - recognising the fetch where codex's handoff item is parsed, since codex gives the realtime
    voice no client tools;
  - keeping `[LAST]` off every stored path.

  But the fetch is bolted on beside existing mechanisms instead of extending them. It adds six
  pieces of state (`fetchDue`, `Delivery.isFetch`, `fetching`, `heldFetch`, `seededContext`,
  `heldContext`) and a fetch clause in about a dozen places across three types.
- **Is anything redundant?** Yes:
  - One fetch is tracked in two actors (S1).
  - The fetch's speak-or-hold rule duplicates the held-result rule (S2).
  - `seededContext` exists only to make up for when the snapshot is taken (S3).
  - Smaller items are S4 to S11.

  S1 and S2 are the debt to fix or record. The rest are cheap.

## From `superpowers:requesting-code-review`

### C1 (Critical): a long reply clipped inside a code block reaches OpenAI as code, and loses its conclusion

**Files:** `plugin/hooks/turns.ts:50` (`clipToEnd`), `plugin/hooks/register.tsx:271`
(`lastText`), `app/Sources/BridgeCore/Text/AnswerShaper.swift:28` (`prose`).

**What happens:**
- `clipToEnd` keeps the last 8,000 characters of Claude's reply from a line start, without
  looking at fences.
- When the cut falls inside a fenced block, the app receives an odd number of fences.
  `prose()`'s `/```[\s\S]*?(```|\z)/` then reads the block's closing fence as an opening one.
  It deletes the prose after it, up to the next fence or the end, and keeps the code body.
- The code body is then redacted by pattern only, cut to its end within 2,000 characters, and
  spoken to OpenAI as `[LAST]`.

**Reproduced** by compiling `prose()` as it is in the tree. The input was:

```
DB_PASSWORD_HINT: hunter2-prod
internal_host = build-07.corp.example
```
followed by a closing fence and "I moved the settings into .env. The deploy is fixed.".

`prose()` returns `DB_PASSWORD_HINT: hunter2-prod internal_host = build-07.corp.example`.
The code-reviewer subagent got the same with a different input.

**Why it matters:**
- No hostile input is needed. An ordinary long answer that ends with a big block and a short
  conclusion is enough: a config dump, a diff, a generated file. The same applies to a long step
  text before an open question.
- Values outside the redactor's patterns pass as they are: an unlisted `KEY=value`, hostnames,
  IPs, proprietary source. So does a PEM block whose `BEGIN` line was cut off.
- README Privacy (`README.md:323`) says `[LAST]` is sent "with code blocks and tables removed".
  That is more than the code enforces (AGENTS.md rule).
- It is also the plan's own Review Focus ("a reply full of code must reach the voice as prose
  with its conclusion").
- `lastDropsCodeAndKeepsTheEnd` (`AnswerShaperTests.swift:43`) and `aLongLastReplyIsClipped`
  (`context.test.tsx:211`) use whole blocks or plain lines, so neither sees an odd fence.
- Results are not affected: they are clipped from the start, and an unclosed opening fence only
  removes the tail.

**Fix:** shape before cutting. In the mod, strip fenced blocks and table rows from `last`
before `clipToEnd`. That is the mod's twin of `AnswerShaper.prose`, and the app's pass then
finds nothing more to remove. At the least, when the dropped head holds an odd number of fence
lines, drop the kept window up to and including its first fence line.

As defence in depth, `prose()` can drop everything before the first fence when the text holds
an odd number of fence lines.

**Tests, one per side:**
- Mod: a reply of a 9,000-character block, its closing fence, then "So the build is fixed."
  The posted `last` ends with the conclusion and holds none of the code.
- App: `prose()` of a text that starts inside a block keeps the prose after the closing fence
  and none of the code.

### R1 (Important): the PR conflicts with `dev`, and the merge decides whether a fetch plays the handoff tick

**Files:** a trial `git merge origin/dev` at `05b534b` conflicts in 13 files:
- `Bridge.swift`, `CallMachine.swift`, `Settings.swift`, `App.swift`;
- `BridgeTests.swift`;
- `CHANGELOG.md`, `README.md` and its six translations.

GitHub reports the PR as `CONFLICTING`. PR #28, now on `dev`, added `confirmsHandoffs` and
`CallEffect.confirmHandoff` on `.handedOff`. The conflict at `CallMachine.swift:197` sits right
between `.handedOff`'s new `[.confirmHandoff, .armResultWindow]` and this PR's
`.fetchAsked`/`.fetchAnswered`.

**Why it matters:**
- The merge is not mechanical. Should a fetch play the tick? README describes the tick as a
  request queued for Claude, and a fetch queues nothing. A merge that copies `.handedOff`'s
  effects into `.fetchAsked` makes the tick lie. A merge that leaves it out makes the voice's
  "on it" for a fetch the one handoff without a cue.
- `VoicePrompt.swift` auto-merges with no conflict. Read as a whole, it now carries both
  PR #28's "a request you do not hand off is lost" and this PR's fetch paragraph. It reads
  coherently: a fetch is a handoff, so an "I'll take a look" before it is allowed. But that is a
  judgement about a merged prompt nobody has run.

**Fix:**
- Merge `dev` into the branch.
- Decide the tick for a fetch and pin it with a `CallMachineTests` row. The recommendation is
  no tick, since the tick means "queued for Claude".
- Re-run `scripts/check.sh`.
- Give the reviewer the merged `VoicePrompt.text` to read once.

### R2 (Important): the bridge's drop guards have no test that can fail

**What's missing:**

### R3 (Minor): a spurious `[FAILED]` can answer a fetch that was just asked

**File:** `Bridge.swift:381-382`.

**What's wrong:**
- `send(.fetchAsked(target))` suspends before `registry.requestContext(…, fetch:)` sets the new
  deadline.
- If an earlier, dropped fetch on the same session left a `fetchDue` that has just expired, the
  one-second sweep can run inside that window. The new fetch is then answered "context not
  available", and the real context that follows is only added.
- Swapping the two calls is no fix: it would let the registry hold a deadline the machine does
  not know.

**Fix:** S1 removes the second owner. Short of that, `requestContext(fetch:)` replaces any
expired deadline in the same call, and the bridge sets the deadline before it yields.

### R4 (Minor): a fetch outside a live line still asks the session and arms the deadline

**File:** `Bridge.swift:376-382`.

**What's wrong:** the machine ignores `.fetchAsked` unless `.live`, but the bridge still calls
`requestContext(fetch:)`. A late handoff item on a closing or connecting line therefore costs a
summary, maybe a model call, for an answer nobody hears.

**Fix:** guard `machine.phase == .live` before asking, or let S1's machine-owned timer decide.

### R5 (Minor): a held context can be added after a newer one

**File:** `Bridge.swift:323-327`.

**What's wrong:**
- A summary is held while the line connects.
- A second one arrives during `send(.connected)`'s effects, when the phase is already `.live`,
  and is added at once.
- The held, older one is then added after it.

This is already in the ledger (Task 4).

**Fix:** add the held line only while it still equals `continuity[session].context`.

### R6 (Minor): an open question's step text falls back to a stale reply

**File:** `plugin/hooks/register.tsx:273`.

**What's wrong:**
- `asking.step || lastReply` uses the previous reply when the step that asked wrote nothing.
  That reply may be many turns old.
- The voice then presents it as what Claude wrote with the question. The spec says the step's
  text.

This is already in the ledger (Task 2).

**Fix:** use the question alone when `step` is empty. S9 does this as a by-product.

### R7 (Minor): the summary stays cached after a voice answer that was lost

**File:** `plugin/hooks/register.tsx:490`.

**What's wrong:** `if (!post) staleSummary()` keeps the summary after a voice turn whose answer
post failed (`LOST_ANSWER`). The voice never heard that answer, which is the condition the spec
gives for calling the summary stale.

This is already in the ledger (Task 2).

**Fix:** also stale it when the post is not taken.

### R8 (Minor): the new default reaches only installs that never saved a setting

**Files:** `app/Sources/BridgeCore/Settings.swift:22,36`, `CHANGELOG.md:20`.

**What happens:**
- `SettingsStore` writes the file only on a change, and then writes every key.
- An install that never changed a setting has no file, and silently flips to on. From then on,
  a summary goes to OpenAI at every line open.
- An install that changed any setting keeps `"autoContext": false`.
- An install that had it on gets the new meaning ("when a line opens" instead of "when it
  becomes the target").

The CHANGELOG's "is now on by default" reads as if it applies to everyone.

**Fix:** say that it applies to installs that never saved settings, or migrate. A migration is
the owner's call.

### R9 (Minor): the smoke's fetch checks are weaker than they look

**File:** `app/Tests/Smoke/fake-session.mjs:130,160`.

**What's wrong:**
- `fetchWasNotARequest` passed in the failed run 1 (`voice-session-context-smoke-run1.log`). It
  fails only when a brief containing "refresh context" reaches Claude. `exactlyOneHandoff` is
  what caught the failure.
- `contextAsks` is logged but not asserted.

**Fix:**
- Assert `contextAsks >= lives.length + 1`: one ask per line opened, plus the fetch.
- Assert that no `Task:` line follows the small talk.
- Keep `exactlyOneHandoff` as the main check.

## From `simplify` (reported, not applied)

### S1 (Important): one fetch is tracked in two actors

**Files:**
- `app/Sources/BridgeCore/Sessions/SessionRegistry.swift:10` (`Delivery.isFetch`), `:66`
  (`fetchDue`), `:171` (`endFetch`), `:234` (the sweep's fetch branch);
- `Call/CallMachine.swift:107` (`fetching`);
- `Bridge.swift:382`, `:514`, `:536-541`.

**Cost:**
- "A fetch is open" lives in the registry and in the machine.
- `Bridge.context` and `Bridge.sweep` each have to check both.
- `requestContext` gains a `fetch:` parameter that two of its three callers pass as `nil`.
- `Delivery`, a request-answer type, gains a flag, and its `text` goes unused because
  `fetchFailed` rebuilds the line.
- The two copies already drift. After a hang-up the registry still holds a deadline, which is
  harmless only because of R2's untested guards. The drift is also what opens R3.

**Simpler form:**
- Make the deadline one of the line's timers: `CallEffect.armFetchWindow(seconds: 60)` and
  `CallEvent.fetchWindowElapsed`, beside `armResultWindow`. The machine answers it with the
  failure line while `fetching` is set.
- The registry keeps only `wantsContext`. `fetchDue`, `isFetch`, `endFetch`, `fetchFailure`'s
  plumbing and the `fetch:` parameter go. Hang-up and Stop cancel the timer the way they cancel
  the others. R3 and R4 disappear.
- The mod's own 60 s stays as the second guard.

Ruling S1 put the deadline in the registry's sweep before this duplication was visible. This
finding asks to reopen that ruling.

### S2 (Important): the fetch's speak-or-hold path copies the held-result path

**File:** `CallMachine.swift:109` (`heldFetch`), `:135` (`graceIfQuiet`), `:197`
(`fetchAnswered`), `:214` (`graceElapsed`), `:220`, `:226`, `:259` (`hangUp`).

**Cost:**
- "Hold while someone speaks, say it after the grace, keep silence from closing the line, clear
  on hang-up" is now written twice: once for `awaited`/`Unheard.isHeld` and once for
  `fetching`/`heldFetch`. Seven transitions carry a fetch clause.
- The next change to the speaking rules has to be made in both places.
- `isAckUnfinished = true` (`:194`) is a hand copy of `.handedOff`'s side effect, as the
  tick will be after R1.

**Simpler form:** two options.
- Smallest: one private `sayOrHold(_ lines:) -> [CallEffect]` shared by `.deliver`'s awaited
  branch, `.fetchAnswered` and `.graceElapsed`.
- Deeper: make the wait a value, `awaited: [Wait]` with `Wait(session, kind: .request | .fetch)`.
  `.handedOff` and `.fetchAsked` become one event. Fetch lines then enter `unheard` as transient
  entries that are dropped once spoken, and are never chimed, seeded or replayed. `heldFetch`
  and every fetch clause fold into the existing code.

Keeping the fetch out of `unheard` is right. Keeping it out of the hold logic is not needed.

### S3 (Minor): `seededContext` makes up for when the snapshot is taken

**File:** `Bridge.swift:36-39`, `:313-327`.

**Cost:** two fields, two resets and a three-part guard
(`held.session == session, held.text != seededContext, machine.phase == .live`).

**Simpler form:**
- Read `continuity[session]` after `await registry.openTasks(of:)`, not before it (`:313` and
  `:314`), and clear `heldContext` right after `initialItems`. Nothing can then be both seeded
  and held, so `seededContext` and the `held.session` check go.
- Do not just clear `heldContext` after `initialItems` with the read where it is now: a context
  that arrives during `openTasks` would then be lost. Two simplify agents proposed exactly that.
- Deeper option: make "context while connecting" a machine event that is held in `.connecting`
  and flushed at `.connected` beside `pending`.

### S11 (Minor): a fetch after a typed turn waits for a fresh summary before `[LAST]`

**File:** `register.tsx:305-343`.

The commonest fetch is "I typed, now tell me what Claude said". That is exactly when the cached
summary is stale, so `[LAST]`, which is already in memory, waits for a full `summarize()` fork:
seconds to tens of seconds of a billed open line. The fake session answers at once, so the smoke
cannot show it.

Ruling "Minor 5" settled the timeout semantics, not this latency. Options:
- tell the mod that an ask is a fetch (a wire change), and post `last` with the cached summary
  at once;
- or measure it by hand first.

Two efficiency notes were judged too small to report: the mod reposts an unchanged context and
redraws the band at every line open, and `clipToEnd` spreads at most 8,000 code points.

## From `security-review`

The candidate pass found one issue at confidence 8 or more. It was verified by compiling the

### SEC1 = C1 (Medium by the skill's scale; Critical in this review): code and secrets of a long reply reach OpenAI as `[LAST]`

This is C1 above; the details are kept in one place. Category: data exposure to a third party
beyond what the docs say.

### Filtered out (confidence below 8)

- **The default flip** (5/10) is kept as R8.

### Checked and found sound

- **Redaction order.** `AnswerShaper.line` runs `flat`, then `Redaction.redact`, then the cut.
  The app never cuts a secret before redacting it; only the mod's earlier cut can (C1).
- **Format injection.** `[LAST]` is still flattened: brackets become parentheses and line breaks
  become spaces. The label is flattened too.
- **No `[LAST]` without a fetch.** The menu, `/live context` and the line opening all pass
  `fetch: nil`. Only the voice's handoff sets `fetching`. `heldContext` carries only the summary.
  `last` is never stored or seeded.
- **A local process.** While a fetch is due, it can post a `last` for the fetched session; it
  cannot create a fetch. SECURITY.md says so.
- **The brief match.** It is a words-only comparison and has no effect on authorization. A miss
  goes to Claude as any request, and a false match costs a context fetch. Both are documented.
- **Permission prompts.** The mod still answers none. A typed turn's `AskUserQuestion` cannot be
  answered by voice.

## What a smoke run should show

`scripts/smoke.sh` was not run. The one real-voice run predates the final prompt fix, and the
fixed prompt has never met the real voice. Run it once after C1 and R1, on the merged prompt.
That run should log:

- **Handoffs:**
  - `handoffs` is exactly the one request: "Please list the files in this folder".
  - No second request reaches the fake session after "look at the chat". Run 1 had a second.
- **The fetch itself:**
  - `contextAsks` is at least the number of lines opened plus one: the line asks, and the fetch.
  - No `Task:` line follows the small talk.
  - The band's unheard count stays 0 around the fetch. Run 1 went to 1.
- **What the voice says:** a `Voice:` line after the small talk names delta, foxtrot or golf.
  Those words exist only in the fake session's `last`, so only a spoken `[LAST]` can contain
  them. A voice that answers from the old `[RESULT]` (alpha, bravo, charlie), as in run 1, fails
  `lastReplySpoken`.
- **Timing:** `openLessThan120s`, `backToListening`, and the line closing after the `[LAST]`
  answer by silence, not by the 60 s fetch failure.

One pass is not proof for a language model. Three passes in a row, plus one by hand in the
language the owner speaks, would show whether the voice keeps the brief in English. If it fails,
the fallback is already documented: the question goes to Claude as a request.
