## Is the architecture elegant enough? Is anything redundant?

**Elegant enough.** One value, two sources, and the rules in pure `BridgeCore` types the tests reach
directly: `LimitsPoll`, `UsageLimits`, `LimitRow`, `CodexLimits.read` against `RPCClient`. A
separate `/v1/limits` is the right shape, as limits run on their own cadence. The voice path has no
new edge in it at all.

**Two weak spots.** The read's sequence (locate, launch, read, close, the kept path) is the one part
that can really go wrong, and it sits in the untested target (S-1). And window ageing is two rules
that do not meet: Codex has `staleAfter`, Claude has "until its reset", and a Claude window with no
reset falls between them (R-2).

**Redundant:** S-2 to S-4. Most is what survived commit `15ffaaf`, which moved from named windows to
any window.

## Findings

Line numbers are at `3d5822b`.

### Important

**R-1. The privacy headline is now false.** `README.md:37-41`, `site/index.html:185`, and the same
sentence in the six translations.

- It says that besides what codex and Claude Code already send, "the app's only traffic of its own
  is for updates", and that the voice line goes to OpenAI "only while it is open". The PR adds an
  authenticated request to OpenAI on menu open, with the call off, that the owner's own use of codex
  did not cause. The new Privacy paragraph says so correctly; the headline still contradicts it, and
  the diff leaves it untouched.
- This is the project's first privacy promise, under "Local by design". The spec's Docs section asks
  for each such sentence to be checked, and AGENTS.md says docs never claim more than the code does.
  "No audio is sent anywhere" was fixed; this one was missed.
- **Resolution:** name the usage read in that sentence, in seven READMEs and the site. A reader who
  stops there must not be told something false.

**R-2. A window with no reset never goes away.** `UsageLimits.swift:131`, `:142`.

- `current(at:)` keeps any window with a nil `resetsAt`, nothing else clears it, and a menu bar app
  runs for weeks. `resetsAt` is optional in the engine's type, and an unparsable string also becomes
  nil. Probed: the last session leaves at 95 % with no reset, and the row stays orange, `95% of 5
  h`, on a reading 30 days old, until the app quits.
- Worse, one undated report also erases a known reset, as a nil on either side takes the newer
  window, so one such reading turns a window that would have expired into one that never does.
- The spec has "the row stays until each window's reset", which does not say what a window with none
  does. A stale orange figure is the one wrong thing this feature can tell the owner.
- **Resolution:** age undated windows by `readAt` in `current(at:)`, for example after
  `LimitsPoll.staleAfter`, and keep a known reset against an undated report. Add a test of each.

### Minor

**R-3. The Codex row is usually absent when the menu opens, then pops in.**
`LimitsPoll.swift:34-37`. The spec says the menu shows the last reading at once. After 15 idle
minutes, the common case, there is none, so the row arrives in the open menu about 2 s later and
moves the minutes, Settings and Quit under the pointer. **Resolution:** keep returning the old
reading while a read is under way.

**R-4. An expired window can take a slot from a live one.** `UsageLimits.swift:146-150`,
`Bridge.swift:544`. Probed: `five_hour` held past its reset, and a reading of `seven_day`, `a` and
`b`: stored are 5 h, week and `a`, shown are week and `a`, and `b` is lost. **Resolution:**
`current(at: time.now)` before merging.

**R-5. A losing arrival still refreshes "Read at".** `UsageLimits.swift:150`. Probed: 40 % held, an
idle session sends 12 % an hour later; the figure stays 40 and "Read at" moves an hour on, so the
tooltip vouches for a figure nobody confirmed. The spec says "changed or was confirmed".
**Resolution:** move `readAt` only when a window was taken or matches what is held.

**R-6. Far dates show only a weekday.** `LimitRow.swift:47-53`. `30-day window resets Tue 10:00` can
mean any Tuesday, and `Read at Wed` was a month old in a probe, so the spec's "showing its age"
fails past a week. The format predates any-length windows. **Resolution:** add the date beyond six
days.

**R-7. The merge needs an exact reset match.** `UsageLimits.swift:143`. Probed: resets one second
apart with 40 % and 12 % give 12, the case the rule exists to prevent. Whether Claude's value ever
jitters is unknown. **Resolution:** treat resets within a minute as one, or leave it and watch.

**R-8. The search path is kept only after a full success.** `App.swift:457`, against "asked for
once" at `:465-466`. A signed-out or API-key user reruns the login shell, `features list` and an
app-server on every read, at most once a minute on menu open, and never gets a row. The first read
also runs the user's shell start-up on a plain menu open. **Resolution:** keep the path once codex
is located.

**R-9. Moving the clock back stops the reads.** `LimitsPoll.swift:21`: `now - lastBegan < 60` is
also true for a negative gap. `UpdatePolicy.isCheckDue` guards this on purpose. **Resolution:** add
`now < lastBegan ||`.

**R-10. Stale wire comments.** `Wire.swift:126-127` and `plugin/hooks/wire.ts:61-64` say other kinds
are ignored, which `Bridge.span(ofKind:)` has not done since `15ffaaf`, and that `percentUsed` is 0
to 100, which is clamped only for display. The wire's own description is wrong in both homes.
**Resolution:** say what the route does.

**R-11. `SECURITY.md` says slightly more than the code does.**

- `:79-80`, "stands until the app quits": a later reading of that window with no reset replaces it
  (`UsageLimits.swift:142`). It goes with R-2.
- `:81-82`, "not fill the menu": true of rows, not of width. Three 32-character kinds measured 1,126
  px at 11 pt, against a 320 px menu. Cosmetic; "add no rows" is exact.
- `:111`, "Every MCP server is off", does not cover this process: that check runs at thread start,
  and the read starts no thread. codex starts no MCP server here (seen in the empty-home run above),
  but LiveBridge does not enforce it. One sentence should say so.
- It does not say the reading is one shared value that outlives its sender, nor that percent is
  clamped only for display. The rest holds: the alphabet and the three-window cap are enforced, and
  `blocked` cannot be faked over the socket.

**R-12. Some labels mislead.** `UsageLimits.swift:39-40`, `:70`. 90 minutes shows `2 h`, 1439 shows
`24 h`, and 90 and 120 minutes both read `2 h`. A kind of `___` shows `7% of    `. Rounding to whole
hours is the spec's wording, so this is a question: `N h` could keep a decimal, or fall back to
minutes.

**R-13. A comment promises what the guard does not do.** `LimitRow.swift:30-32` says it clamps
because `Int(_:)` traps, but `min`/`max` pass NaN through and `Int(NaN)` traps. Confirmed on a value
built directly. It cannot arrive over JSON today, as the decoder refuses it. **Resolution:** a
one-line `isFinite` guard.

**R-14. "Delivered" overstates the plan.** `docs/trail.toml:16-17`, the spec's status, and the
plan's line 61, "checked in Task 9". The PR body says the matrix was not walked, and the Claude
figures in the owner's look were example data. **Resolution:** walk it, or say delivered in part.
The lifecycle below is reasoned, not run.

**R-15. The native row is a platform finding with no home.** `StatusMenu.swift:180`. That `.help`
does not show on a disabled hosted row, and that a tooltip therefore means a native item that
highlights, lives only in the spec. The next menu row will hit it. **Resolution:** a line in ADR
0001.

**S-1. The read's sequence is in the untested target.** `App.swift:452-480`. It also re-types
`launchCodex`'s locate-and-launch and `offeredVoices`' close. Removing the `defer` close would leak
a codex per read and pass CI. **Resolution:** a small reader in `BridgeCore` behind an injected
launch, shared with `offeredVoices`; `AppModel` only wires it.

**S-2. The row's text is written twice.** `LimitRow.swift:21-23`, `StatusMenu.swift:179-209`.
`limitTitle` rebuilds the join and the "blocked" rule by hand, the tests read only `text`, and
`item.title` is set then replaced. **Resolution:** `LimitRow` exposes ordered runs with a tone;
`text` joins them and the app only colours them. Keep `item.title` only if it serves accessibility,
and say so.

**S-3. `isKnown` and "known windows first" decide nothing today.** `UsageLimits.swift:62-67`,
`:118`. Sorting already ranks minutes before kinds. Codex gives at most two windows and is never
merged, and Claude's only `.minutes` are the two known ones, so a third case cannot occur. The test
passes on a built case. **Resolution:** sort, then `prefix`, unless the spec's rule is wanted for a
future source.

**S-4. Smaller redundancies.** `label`, `windowName` and `isKnown` each re-snap what `init` already
snapped, and repeat one length switch. `isBlocked` in `merging` is never true for Claude. Kind
mapping and ISO parsing sit in `Bridge`, not in `Limits/`. A POST with unchanged figures still
publishes, as `readAt` moved, once per session; bounded by the engine's whole-point moves, so no
action unless R-5 is taken, which ends it.

Efficiency otherwise: the menu never waits on the read, and a read costs two codex starts and about
2.2 s, on menu open only. Reusing the live call's client would save one but touch the voice path,
which is the wrong trade.

## The points asked about

**Any-length windows.** They hold. New lengths and new kinds show, nothing tested crashes, and an
unexpected reply gives no row and no error: null windows, strings for numbers, `1e308`, `resetsAt`
up to `1e300`, zero or negative minutes, odd kinds and missing buckets. On Claude's side one bad
field gives a 400 and no row, which the spec allows.

**`/v1/limits` as an attack surface.** No HIGH or MEDIUM finding.

- `kind` is checked byte-wise, not by regex, so there are no anchors to escape: a trailing newline,
  NUL, Cyrillic, fullwidth, RTL and combining characters are all dropped. `five_hour\n` does not
  alias `five_hour`.
- The cap is enforced in `UsageLimits.init`. 10,000 windows left three, and known lengths stay, so
  junk kinds cannot evict them. A 358 KB body gets 413.
- Percent is clamped at display. `NaN`, `Infinity` and `1e999` are refused by the decoder.
- Far dates parse or fail without a crash, in eight calendars.
- A body reaches only the Claude row: not the status, the voice, `continuity.json` or a log. The
  title and tooltip are plain strings. An unjoined session is ignored. No body can start codex.
- On the Codex side the same `launch` gives the same argv. The reply stays in a local value, only
  the window fields and `ordinaryUsageAllowed` are read, and `accountId` is neither kept nor logged.
- One sender overwrites every session's figures, by design and as documented. Considered and
  rejected: a stale `kind`, duplicate windows, `/live status`, a hostile `PATH` beyond what exists.

**Merging; a reading outliving its session; past its reset.** Sound for one account: keyed by span,
later reset wins, and an idle session cannot lower a figure, except R-7. Nothing clears a reading on
leave, removal or the sweep, by design; `/clear` is fine, as it is not keyed by session. Past its
reset a window is left out at each menu open, so a stale orange figure with a known reset does not
outlive it. The gaps are R-2, R-4 and R-5.

**The read and the voice.** By reading, nothing touches the call. The read has its own process,
pipes and process group, app-server talks over stdio so no socket is shared, and every wait is
bounded, about 63 s at worst, so `isReading` cannot stick. `/v1/limits` passes through the same
`changed()` the sweep already runs. At quit a child in its 2 s window relies on stdin EOF, as the
voice's does.

**Not settled:** whether a second app-server on the same `CODEX_HOME` can disturb a live one (auth
refresh, local state). `offeredVoices` is a precedent, but a rare path, and this one fires on every
menu open. Only a run can settle it: open the menu while listening, which spends no voice, and, if
the owner agrees to spend it, once on a live line.

**Tests that cannot fail.** The PR's claim is true. All eight listed mutations failed the named
tests. Of 34 others, 32 failed too, and all 7 mod mutations. The two survivors are dead code, not
weak tests: `isBlocked` in `merging` (S-4), and the fractional-seconds fallback at
`Bridge.swift:566`, which `.iso8601` made unneeded on this macOS; keep it unless macOS 14 is
checked. One gap remains: S-1.

**Docs, translations, the wire rule.** The wire rule is met: three files together, both sides read
`limits.json`, no personal data; R-10 is the comments. CHANGELOG and the overview match the code,
apart from R-1 and R-11. All six translations carry every clause of the two new paragraphs; Hindi
and zh-CN say "not published" where English says "not documented", which is close enough. That is a
reader's check, not a native speaker's.

**The lifecycle the PR did not walk, reasoned only.**

| Case | Result |
| --- | --- |
| Menu open while listening or live | A separate process; no Bridge or audio path is touched. The row may pop in (R-3). |
| Codex missing | `notInstalled`, swallowed: no row, no banner. Claude's row is unaffected. |
| Signed out or API key | An error, swallowed: no row; a reading stands up to 15 minutes. R-8 applies. |
| App restart with a joined session | The next poll rejoins, `joined()` fires, the reading returns. Tested. |
| Last session leaving | The row stays until each window's reset, for ever with none (R-2). |

The floor holds: `$.session.usage()` and `session.measure` validate and pass 84 of 84 tests on
2.1.301. A new mod on an old app gets a 404 and ignores it, with no rejoin; a mutation confirmed it.

### The points asked about

**Undated windows.** Sound. Every undated window in a merged reading comes from `newer`, because an
undated window that is not mentioned is dropped, and one that is mentioned is taken. Taking one sets
`confirmed`, so `readAt` is that arrival's. So the 15 minutes count from the report that said it: a
dated window's arrival cannot stretch them, and a losing arrival cannot leave them running on an old
time. A known reset now survives an undated report, with the higher percent.

**The 15-minute expiry.** One number with one home, `UsageLimits.undatedLife`, which
`LimitsPoll.staleAfter` takes. Exactly 15 minutes stands and one second more goes, tested. It reads
`readAt`, which is why the above matters.

**Resets within 60 s as one.** Sound. The comparison is `abs(…) > 60`, both sides of it are tested,
and the window is kept whole, not mixed. It cannot merge two real windows: the held one has been
dropped by `current(at:)` once its reset passes, and the next window's reset is a window later. A
reset that creeps forward heals itself, as the comparison is always against the held reset. The rule
is not transitive, and does not need to be.

**The old reading during a read, and a read that fails.** Sound, and `finish` is reached on every
path, so `isReading ||` cannot pin a reading. A failed read removes the stale row at once, also with
the menu open, which is honest. Three limits to know, all accepted by the spec's wording and none
worth a change:

- `LimitRow` still applies `current(at:)`, so a stale reading keeps only windows that are current.
  If none is, the row is absent during the read and pops in, the old R-3 case, now rare.
- An old `blocked` shows for the length of the read.
- An old reading has no mark of its age but its tooltip.

**`readOnce`'s awaited close cannot hang a menu open.** The menu does not wait on the read at all:
`refreshLimits` returns at once and the read is in a `Task`. The close is bounded:
`JSONRPCClient.close()` waits at most 20 × 100 ms, then `SIGKILL`, with no unbounded await. That
matters more than the menu, because a close that hung would have kept `isReading` true for good,
with the reading frozen and no more reads. It cannot. The read's worst case is now about 65 s, and a
reading lands up to 2 s later than before if codex is slow to end, which is a fair price for
`aFailedReadClosesCodex`. `refreshLimits` itself stays in the untested target, so nothing tests that
`finish` always runs; that is by reading.

**`LimitRow.runs` kept the orange rule.** Yes. `isNear` is set only on a figure, from the same
rounded percent and `nearPercent`, so 89.5 still shows 90 in orange. Separators and `blocked` take
the quiet colour, which is orange when blocked, as before. The colouring in `limitTitle` is by
reading, as that target has no tests, but it is now one line. `runs.joined()` is `text`, so the two
cannot drift, the aim of S-2.

**Nothing new broke.** The merge's new `confirmed` flag, `current` before merging and the unsnapped
`label` were each traced. `.minutes` built directly is no longer snapped, which only tests do; the
one test that relied on it moved to `init`.

### The rejected items

**S-3, known windows first: agree.** It decides nothing today, but the spec states it as a rule for
sources yet to come, it costs two lines, and a test pins it. A finding about today's sources was the
wrong measure for a rule written for tomorrow's.

**The rest of S-4: agree.** `isBlocked` in `merging` is one value carried through, kind mapping and
ISO parsing in `Bridge` are where the socket's input lands, and a publish per confirmed arrival
stays bounded by the engine's whole-point moves. None earns a change.

**The other half of S-1, sharing the read with `offeredVoices`: agree.** The two differ in the kept
search path, and `offeredVoices` is rare. What mattered was the close and the test, and `readOnce`
gives those. `offeredVoices` keeps its fire-and-forget close, which is fine for a path that rare.
