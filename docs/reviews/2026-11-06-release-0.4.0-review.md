## Does an installed 0.3.0 update cleanly?

**Yes, on reading and on the data files. It has not been run for real.**

The update is performed by the 0.3.0 app's own `Updater.install`, in this order: download, verify,
stage, wait for quiet, **update the mod on disk**, stop the call, **swap the app**, relaunch. Open
sessions keep their loaded mod until they restart. So the normal state after an update is a 0.3.0
mod talking to a 0.4.0 app, and the reverse exists for seconds, or for longer in the two cases
below.

### What is stored

| File | 0.3.0 to 0.4.0 |
|---|---|
| `continuity.json` | **Reads.** Written by 0.3.0's code and read by 0.4.0's: lines, speakers, context and order all kept, and it round-trips. The new fields are optional. A file that did not decode would start empty, and it does not come to that. `keptLines` grows from 24 to 64, which an old file only sits under |
| `settings.json` | **Reads.** `autoContext: false` becomes the pause on; the default stays off, as the changelog says, and the mapped value survives a save |
| Usage meter, update state, `UpdateRecord` | Source files identical |
| The mod's store | **Reads.** Same key, `joined:<id>`. `pending`, `followUp` and `turns` keep their shape, and `typed` and `prompts` default to empty. A 0.3.0 snapshot with a running voice turn gave the right turn and a clean end, run on the tracker |

A gap is not missed across the update. A 0.3.0 file reads as current, which alone would be wrong,
as typed turns never reached it. But a session on the old mod does not sync, so it still asks for a
summary. A snapshot with no `hasGap` notes a gap, and `/live on` after a restart notes one too, so
the first line of a new mod's session gets its summary.

### A 0.3.0 mod with a 0.4.0 app

The usual case, and it works as the docs say.

- `join`, `answer`, `activity` and `context` keep their shapes, and the app's new fields are
  optional.
- The poll adds `status.isMuted` and `forRequest` to `reply`. 0.3.0 reads neither and needs neither.
- `session.syncs` is false, so each line asks for a summary as 0.3.0 did, and `Bridge.needsContext`
  holds that back under the pause, which an `autoContext: false` owner now has.
- `poll` opens no request for a reply from such a mod (`SessionRegistry.poll`), which is what the
  README's limit describes.
- No Claude usage row shows until the session restarts, and Mute works from the menu. Both are
  fine: the row is left out, not shown wrong.

### A 0.4.0 mod with a 0.3.0 app

This lasts seconds in an update. It lasts longer if the swap fails (`modAlreadyUpdated` says so) or
if the owner updates the mod by hand. It works, and nothing typed leaves:

- `/v1/sync` and `/v1/limits` get 404 with no effect on the link. The first notes a gap each time,
  which costs a store write and at worst a dropped `/live context`.
- Extra join and activity fields are ignored.
- `forRequest` is absent, which the tracker handles.
- The band hides Mute, as `isMuted` is undefined, so there is no dead button.
- A typed question reaches the voice, and the spoken reply can hold a line for 120 s; the changelog
  says so.

The floor rises from 2.1.289 to 2.1.301, but the changelog's reason is that 0.3.0's hooks already
did not load on 2.1.296, so that is no new break.

## Findings

Both Minor.

**R-1. The Note omits the update itself.** `CHANGELOG.md`, `[0.4.0]`, Note. This review is the only
check of the 0.3.0 to 0.4.0 path, and no real update ran. The Note lists what was not checked, so
one clause belongs there: "the in-app update from 0.3.0 was read and its data files tested, not
run".

**R-2. Sync reaches existing owners with no notice in the app.** `Settings.swift`, `release.yml`.
With 0.3.0's default settings the update leaves the pause off. So after Install and a session
restart, what the owner types in a joined session goes to OpenAI once a line opens. That is the
owner's decided default and the docs say it, but the changelog is the only place an updating owner
would see it, and `gh release create --generate-notes` builds the Release page from PR titles. Add
two sentences to the Release body after the workflow runs, with `gh release edit`. If an owner
reads one thing before Install, it should be this.
