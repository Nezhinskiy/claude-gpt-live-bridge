# Review of PR 34: a line an answer opens says that answer at once

- Pull request: [getLiveBridge/LiveBridge#34](https://github.com/getLiveBridge/LiveBridge/pull/34),
  `fix/reopened-line-speaks-at-once` → `dev`, one commit (`01ec140`).
- Reviewed against `origin/dev` (`02aa5c5`) with `superpowers:requesting-code-review` (an
  independent reviewer plus my own pass), `simplify` (reuse, simplification, efficiency and
  altitude) and `security-review`, held to an open-source project's highest standards. Findings
  only. Nothing was fixed or pushed to the PR branch, and `scripts/smoke.sh` was not run.
- Evidence: throwaway probe tests replayed each path below through the PR's `CallMachine`, and a
  prototype of the suggested fix (S-1) was run in a scratch worktree. With the prototype, all
  312 existing Swift tests passed, plus the probes. None of it is committed.
- Verdict: **merge with fixes.** 0 Critical, 5 Important, 9 Minor. Security: no findings.
  I-1 and I-2 are behaviour bugs that probes confirmed. I-3 and I-4 are docs that now contradict
  the code or claim more than it does. S-1 is the shape that fixes I-1 and I-2 together.

## Is it elegant? Is anything redundant?

**Elegant: partly.**

- What is right:
  - The decision is in the right layer. The pure machine chooses between `.speak` and
    `.addContext`, and the bridge only runs the effect.
  - It reuses the `.speak` effect that the awaited-result path already uses, so there is no new
    effect, wire change or codex call.
  - The change is small, and the new mixed-case row (`theOpenedLineGetsOtherUnheardLinesAsContext`)
    tests the right thing.
- What is not right:
  - It adds a second flag on `Unheard`, `opensLine`, for an idea the machine already has.
    `isHeld` already means "a line owed a `.speak` once nobody is speaking". The line that
    opened a closed line is that same thing, with the connect as the moment it becomes owed.
  - Because the idea is new rather than reused, it misses the parts of the existing rule that
    already work:
    - `rename` copies `isHeld` but not `opensLine` (I-2).
    - The grace rule that holds `isHeld` while someone speaks does not apply to it (I-1).
    - It needs a clearing loop that `hangUp()` already makes dead (S-2).
  - The prototype in S-1 uses `isHeld` instead. It has fewer lines and fixes both bugs.

**Redundant: yes, in three places.**

- The clearing loop at `CallMachine.swift:175` (S-2).
- The partial overlap between `opensLine` and `isOpeningForResult` (S-4).
- The 5-8 s figures, which are now written in four places beside their home in ADR (n) (R-8).

## 1. `superpowers:requesting-code-review`

**Strengths.**

- Test-first: the PR says both new rows failed before the change.
- The overview says plainly that `appendSpeech`'s timing is not measured.
- These paths behave correctly; a probe replayed each one:
  - A failed connect, a remote close, `conversationChanged`, and a hang-up followed by a reopen
    by speech all rebuild `Unheard` through `hangUp()`, which clears the flag. The reopened
    line gives everything as context.
  - Stop resets the machine.
  - A spoken opener is tracked as heard exactly as a `.speak` on a live line is. It is in
    `pending` when `assistantSpeaking` fills `replyCanSay`, and `says()` removes it, so the
    20 s rule then closes the line without a chime.
  - `withdraw` drops the flag together with its line.
- `appendSpeech` adds no new way to fail:
  - Both calls return `{}`, and on V3 both become `session.context.append` (ADR 0001 (b)).
    `appendSpeech` differs only in `channel: "speakable"`.
  - Item (b) already called `appendSpeech` on a fresh session with no user turn. It was not
    spoken, but it was not refused either, and nothing closed.
  - `RealtimeSession.speak` has the same `no voice session open` guard as `addContext`. The
    bridge runs it under the same `try?` (`Bridge.swift:271`), so a throw leaves the line
    unheard, and it chimes when the line closes.
  - `initialItems` already leaves unheard Claude lines out of the seed (`Continuity.swift:67`),
    so the opener is not both seeded and spoken.

### Important

- **I-1. The owner speaking while the line connects is not covered by the hold rule.**
  `app/Sources/BridgeCore/Call/CallMachine.swift:174`, with `(.connecting, .speechStarted)`
  falling through to `default` at `:229`.
  - Problem:
    - On a line that an answer opened, `isSoundOn` is never set while connecting. Only
      `(.listening, .speechStarted)` and `(.live, .speechStarted)` set it. `speechEnded` resets
      it in every phase, so the two are not symmetric.
    - `.connected` then sends `.speak` even while the owner is talking. Probe:
      `start, opening(result), speechStarted, connected` gives
      `[.flushPreroll, .speak(result), armSilenceTimer(20), .problem(nil)]`.
    - On a live line, the same `.speak` is held until everyone is silent, then given after the
      0.8 s grace (`isHeld`, `graceIfQuiet`; ADR 0001, "Decision: the line waits for a
      handoff's result").
  - Why it matters:
    - This case is likely. An opening line makes no chime, so the owner who sees Claude finish
      often starts talking during the 1-3 s connect.
    - Before this PR, a line given as context while the owner spoke was harmless. Now
      speakable text arrives mid-utterance, so the voice may talk over the owner, or start the
      answer and be cut off.
    - Side effect of the same gap: the silence timer is armed for 20 s instead of the 90 s
      noise cap while the owner is still making sound.
  - Fix:
    - Add `case (.connecting, .speechStarted): isSoundOn = true; return []`.
    - In `.connected`, give the opener with `.speak` only when `!isSoundOn`. Otherwise leave it
      held: the existing `speechEnded` → `armGrace` → `graceElapsed` path says it. S-1 does
      exactly this.
    - Add one table row for it. The prototype gives `[.flushPreroll, armSilenceTimer(90),
      .problem(nil)]` on connect, then `armGrace` on `speechEnded`, then `.speak(result)` on
      `graceElapsed`.
- **I-2. A `/clear` rename during the connect loses the flag.**
  `app/Sources/BridgeCore/Call/CallMachine.swift:253`.
  - Problem:
    - `rename` rebuilds each entry as `Unheard(line: moved($0.line), isHeld: $0.isHeld)`, so
      `opensLine` falls back to `false`.
    - Probe: `start, opening(result), rename(alpha → new), connected` gives
      `[.flushPreroll, .addContext(result'), arm, .problem(nil)]`, with no `.speak`.
    - The join handler keeps a connecting line across a rename, so the path is reachable. It is
      a narrow race, and the answer then falls back to exactly the late-or-silent behaviour this
      PR fixes.
  - Root cause: `Unheard` is rebuilt with its memberwise initialiser in three places (`:215`,
    `:253`, `:263`), so any new field silently gets its default (S-3).
  - Fix:
    - Either fold the flag into `isHeld` (S-1), which `rename` already preserves, or make
      `line` a `var` and move the session in place:
      `for i in unheard.indices where unheard[i].line.session == old { unheard[i].line.session = new }`.
    - Add the probe as a test. A natural home is beside `aRenamedSessionKeepsItsWaitAndItsResults`.
- **I-3. The ADR still records the old decision.**
  - Where:
    - `docs/adr/0001-platform-findings.md:426`: "Decision: a result opens the closed line"
      still says the new session "gets the line as context".
    - `docs/adr/0001-platform-findings.md:323-328`: the "### Codex" decision bullet still says
      results go with `appendText`, and only a waited-for handoff's result goes with
      `appendSpeech`.
  - Problem:
    - Both are now false.
    - `docs/architecture/documentation.md` says superseded prose is removed in the same change,
      and a change of which channel the decision uses belongs in the ADR, not only in the
      overview.
    - That decision is dated and attributed to the owner, so the amendment should say who
      decided it and when.
  - Fix:
    - Amend both passages: the opener goes with `appendSpeech`, any other unheard line stays
      context, and how fast the voice speaks it is not yet measured.
    - Add the measuring run's result to item (n) once it exists (see "What one measuring run
      should show").
- **I-4. The CHANGELOG, the commit title and the code comment claim more than the code
  enforces.**
  - Where:
    - `CHANGELOG.md:11-12`: "is given that answer to say at once, not as context the voice
      took 5 to 15 seconds to take up, or left unsaid".
    - `app/Sources/BridgeCore/Call/CallMachine.swift:172`: "is said at once".
    - The commit title: "says that answer at once".
  - Problem:
    - The code only changes the call. `RealtimeSession.swift:223-226` and the overview both say
      that whether and when a V3 voice says speakable text is the model's choice. The only
      measurement of `appendSpeech` was on a line with a handoff pending (item (b)), never on a
      freshly seeded line.
    - AGENTS.md: "Docs never claim more than the code enforces."
    - "5 to 15 seconds" also mixes two measures. The owner-perceived 7-15 s from the PR body
      includes the connect, while the voice's own delay is 5.4-7.7 s in item (n), which the
      overview gives as 5 to 8 s.
    - "or left unsaid" reads as if the silent case is fixed. The README limitation at
      `README.md:376-378` rightly still says it is not.
  - Fix:
    - CHANGELOG: "A voice line that Claude's answer opens is given that answer as speakable
      text (`appendSpeech`, the call used for a result the line waits for), not as context,
      which the voice took 5 to 8 seconds to take up or left unsaid." Leave out any new timing
      until it is measured.
    - Comment: "What opened the line is given to say (appendSpeech) ...".
    - If the commit is reworded, use "gives that answer to say" rather than "says that answer
      at once".

## 2. `simplify`

There were four lenses: reuse, simplification, efficiency and altitude. Nothing was applied.

- Efficiency: no findings. The `.connected` branch runs once per open.
- The nit that `unheard` is walked twice (map, then clear) disappears with S-2.

### Important

- **S-1. `opensLine` re-implements `isHeld`. Fold it in.**
  `app/Sources/BridgeCore/Call/CallMachine.swift:95-96, 159, 174-175`.
  - Problem:
    - `isHeld` already means "said with `.speak` once everyone is silent". The opener is that
      same state, owed from the connect.
    - A second flag means every rebuild site must copy both (I-2 shows one that does not), the
      opener misses the grace rule (I-1), and the next "speak this" case is likely to add a
      third flag.
  - Fix. This is verified: in a scratch worktree, all 312 existing Swift tests pass with it,
    and the probes for I-1, I-2, a failed connect, a remote close then reopen, and the heard
    tracking all give the expected effects.

    ```swift
    private struct Unheard: Sendable {
      let line: VoiceLine
      /// To be said (`speak`) once everyone is silent: an awaited result that arrived while
      /// someone spoke, or the line that opened the closed line.
      var isHeld = false
    }
    // (.listening, .deliver(let result, let opensLine)):
    unheard.append(Unheard(line: result, isHeld: opensLine))
    // new: the owner may start speaking while a line an answer opened connects
    case (.connecting, .speechStarted):
      isSoundOn = true
      return []
    // (.connecting, .connected):
    let quiet = !isSoundOn
    let lines: [CallEffect] = unheard.compactMap {
      !$0.isHeld ? .addContext($0.line) : quiet ? .speak($0.line) : nil
    }
    if quiet { unheard = unheard.map { Unheard(line: $0.line) } }
    return [.flushPreroll] + lines + [armSilence(), .problem(nil)]
    ```

  - What it does:
    - It drops the field and the loop.
    - `rename` already keeps `isHeld`, so I-2 is fixed.
    - The live grace path (`speechEnded` → `graceIfQuiet` → `graceElapsed`) takes over when
      the owner is speaking, so I-1 is fixed.
    - `hangUp()` already clears `isHeld` on a failed or remote-closed connect.
  - The altitude reviewer suggested the same fold, but without the `isSoundOn` check, on the
    grounds that "nobody is speaking on a line that has just opened". The I-1 probe shows the
    owner can be.

### Minor

- **S-2. The clearing loop is dead code.** `app/Sources/BridgeCore/Call/CallMachine.swift:175`.
  - Problem: only `(.connecting, .connected)` reads `opensLine`. Every way out of `.live` goes
    through `hangUp()` or `end()`, and both clear the flag before the machine can reach
    `.connecting` again.
  - Fix: delete it, or, if kept as a deliberate "consumed here" marker, say so in a word. S-1
    removes it either way.
- **S-3. `Unheard` is rebuilt by hand in three places, and each rebuild drops any field it does
  not name.** `app/Sources/BridgeCore/Call/CallMachine.swift:215, 253, 263`.
  - Problem: this is the mechanism behind I-2.
  - Fix:
    - Make `line` a `var` and mutate in place. For `rename`, see I-2.
    - For the resets: `for i in unheard.indices { unheard[i].isHeld = false }`.
    - Then a future field is either kept or reset on purpose.
- **S-4. `opensLine` partly duplicates `isOpeningForResult`.**
  `app/Sources/BridgeCore/Call/CallMachine.swift:115, 162, 240`.
  - Problem: while connecting, `isOpeningForResult` is "some entry has `opensLine`", except
    after the opener is withdrawn.
  - Fix:
    - Keep `isOpeningForResult` if R-9's behaviour stays.
    - If the owner takes R-9, derive the `withdraw` guard from the held flag and drop the
      separate Bool.
    - The PR body's claim that the flag "was set but did not change what was sent" is true but
      incomplete: `withdraw` reads it.

## 3. `security-review`

**No findings.** Nothing reached the 8/10 confidence bar, so no false-positive filtering was
needed. These are the vectors examined, and why each one is either not new or not exploitable:

- **Untrusted text causing an action without the owner.** Not new.
  - The same text already reached the voice before this PR, as `appendText` with role `user`,
    which reads as the owner's words. The live-line `.speak` path already used the speakable
    channel.
  - A handoff still needs the voice to call its tool and go through `route`, and Claude Code's
    permission prompt still applies. Nothing here answers that prompt.
  - Steering the model through the spoken text is prompt injection, which the review
    excludes.
- **Cross-session exposure.** Not possible.
  - `opensLine` is true only for the target's own line while its conversation holds an owner
    turn (`Bridge.swift:425-430`).
  - A target change while connecting hangs up (`conversationChanged`).
  - The line is seeded only with the target's conversation.
- **Speaking what was withheld before.** No. The same set of lines was already given to the
  voice, and the rule for when a line opens is unchanged.
- **Injection or code execution.** No. The text goes to codex as a JSON-RPC string value
  (`RealtimeSession.swift:227-233`), and `AnswerShaper`'s line shape is unchanged.

## What one measuring run should show

`scripts/smoke.sh` does not exercise this path. Its result arrives while the line still waits for
it, so the result goes out as a live `.speak`. The measurement needs item (n)'s probe set-up:

- the debug app with `--fake-mic`, a spoken request at 6 s and silence after;
- `resultWindowSeconds` set to 0;
- the fake session answering 30 s after it takes the request, so the result arrives after the
  first line has closed and opens the second one;
- no nudge.

Use at least four runs, since the baseline was silent in 1 of 4. Measure the same quantity
item (n) did: the time from `live` to the first assistant `transcript/done`. A pass looks like
this:

- The voice says the result in every run. `pending` empties through `says()`, and the line
  closes after the 20 s rule with no chime.
- The first segment ends in about 2 s, in line with the nudged runs in item (n) (1.3 to
  2.0 s), against 5.4 to 7.7 s with `appendText`. Also log the time from the mod's
  `/v1/answer` to the first `assistantSpeaking`, the owner-perceived gap that was 7 to 15 s.
- No `thread/realtime/error` and no `closed` follow the `appendSpeech`.
- No new handoff and no repeat of the result.
- With I-1 fixed, one extra run with a short utterance queued at the connect should show the
  result said only after the utterance, plus the grace.

Record the outcome in ADR 0001 (n). Then the overview's "not yet measured", and possibly the
README limitation at `README.md:376-378`, can be updated.
