## Verdict

**Merge after fixes.** No Critical findings. 3 Important, 13 Minor. The security pass found no
vulnerability.

Every microphone path I and the reviewer seat could construct releases the microphone and
keeps it released while muted (the table below). The three Important findings are:

1. The native guard for the macOS-prompt window has no test, and it is the only guard on one
   privacy path (CR-1).
2. Mute re-arms the silence timer on a quiet open line. The docs then say something the code
   does not do: "closes as it would without Mute" (CR-2).
3. The docs ship the claim "macOS's indicator shows it" before anyone has checked it by hand
   (CR-3).

**Is it elegant?** Mostly yes, and much better than the plan the spec review saw.

- **The page has one rule.** `microphone.js` sends every capture through `attach`, and one
  generation token decides whether a capture may be kept. It is pure and tested.
- **The machine reuses an existing event.** Mute is `[.muteMicrophone] + handle(.speechEnded)`,
  so a held result keeps its grace.
- **`createLineAudio`** lifts the hold and pre-roll state out of `audio.js`, so it can be tested.
- **One part falls short: the native guard.** The window while macOS's prompt is up is guarded
  by two counters and a `muteCancels:` flag in `AudioHost` (`AudioHost.swift:26-30, 117-124`).
  That is a second staleness mechanism. It lives in the one target with no tests, and two fix
  commits in this PR (a17ebab, then 71b432e a minute later) were needed to get its asymmetry
  right. The deeper change is to let `Bridge` own the permission step and re-check the
  machine's own state after it (CR-1).

**Is anything redundant?**

- **Not redundant: the three mute states.**
  - `CallMachine.isMuted` is the policy.
  - The page's `muted` is the enforcement, and it needs its own copy for the device changes it
    handles alone.
  - The `stops`/`mutes` counters cover a window neither of the others sees: the native prompt,
    before the page is asked.
  - One counter cannot replace the two, because a Mute must cancel a waiting Unmute but not a
    waiting Start. The machine's state can, though (CR-1).
- **Removable** (all Minor):
  - API used only by the tests (SI-1);
  - the stored `StatusPresentation.isMuted` (SI-2);
  - three copies of the same `do/catch` (SI-3);
  - `mute`/`release` near-copies (SI-4);
  - a dead error message (SI-5);
  - the band's `mute`/`unmute` pair (SI-6);
  - a third idempotence guard (SI-7).

## superpowers:requesting-code-review

### CR-1 · Important · `AudioHost.swift:26-30, 61-91, 117-124`: the native prompt guard has no test, and it is the only guard on one privacy path

**Problem.**

- `stops` and `mutes`, and `mayTakeMicrophone(muteCancels:)`, decide whether a Start or an
  Unmute may still take the microphone once macOS's prompt has been answered.
- **This guard alone protects one sequence:** Unmute while the prompt shows, then Mute, then
  the owner grants. Here `LB.mute()` is a no-op, because the page is still muted. Without
  `mutes == mutesBefore`, the late `LB.unmute()` takes the microphone while every surface shows
  Muted. The page token cannot help, because the page has not been asked yet.
- **The rule is asymmetric and easy to break.** A Mute must not cancel Start, because the page
  records the mute and `listen` must still create the context. `a17ebab` got this wrong and
  `71b432e` corrected it a minute later.
- **Nothing tests it.**
  - None of `4792205`, `a17ebab` or `71b432e` adds a test, which breaks AGENTS.md's "a failing
    test before the change".
  - The `LiveBridge` target has no tests at all, so any refactor can undo the guard silently.
  - The guard is also a second rule the spec does not mention: its "What enforces it" says "one
    rule in the audio page".
- **The `stops` half fixes an older bug that nobody recorded.** On `dev`, a Stop during Start's
  first-run prompt was followed by `LB.listen`, so the microphone opened after the call was off.
  The CHANGELOG does not mention it.

**Fix.** Move the rule to BridgeCore, next to the state it depends on, test-first. Preferred:

- Add `func microphoneProblem() async -> Problem?` to `AudioSide`. Today's `askForMicrophone`
  already fits that signature.
- In `Bridge.run`, for `.startLocalVAD` and `.unmuteMicrophone`:
  1. Await `microphoneProblem()`.
  2. On a problem, end the call as `audioEvent(.failed)` does.
  3. Otherwise re-check the machine. Start proceeds while `phase != .off`. Unmute proceeds while
     `phase != .off && !isMuted`.
  4. Then call `startListening()` or `unmuteMicrophone()`, which become plain page calls.
- `AudioHost` loses both counters and `mayTakeMicrophone`. The asymmetry then reads straight
  from state.
  - A Stop and then a new Start during the prompt makes both proceed. That is harmless: `listen`
    returns at once when `ctx` exists.
  - So is an Unmute, Mute, Unmute sequence: `mic.unmute()` is idempotent.
- Test it with a `FakeAudio.microphoneProblem()` that blocks on a continuation, the pattern
  `finishLaunch` already uses. Rows:
  - Stop during Start's prompt → no `startListening`.
  - Mute during Start's prompt → `startListening`, after `muteMicrophone`.
  - Mute during Unmute's prompt → no `unmuteMicrophone`.
  - Stop during Unmute's prompt → no `unmuteMicrophone`.
- Alternative: a small pure `MicrophoneTakes` type in BridgeCore that `AudioHost` holds, tested
  by the same four rows. It is less general, but it changes no protocol.
- Either way, add a CHANGELOG "Fixed" line: a Stop during the first microphone prompt no longer
  opens the microphone after the call ended.

### CR-2 · Important · `CallMachine.swift:162-165`, README.md:233-235 and 8 other places: Mute re-arms the silence on a quiet open line, and the docs say it does not change when the line closes

**Problem.**

- **What the code does.** `.mute` returns `[.muteMicrophone] + handle(.speechEnded)`, and
  `.speechEnded` on a live line always arms the silence timer (`:170-172`). The row
  `muteOnALineAResultOpenedKeepsTheFirstWordWait` pins the re-arm too, as a fresh 5 s.
- **The cost.** A line that has been silent for 18 s would close in 2 s. After Mute it stays
  open 20 s more, billed. Each Mute after an Unmute re-arms again, so a Mute/Unmute pair every
  15 s keeps a silent line open with no limit. A line nobody speaks on should close.
- **What the docs say instead.** All of these say an open line "closes as it would without Mute":
  - README.md:233-235;
  - the same sentence in README.es, .fr, .hi, .ru, .uk and .zh-CN;
  - CHANGELOG.md:16-17;
  - docs/architecture/overview.md:48-49;
  - the spec, :28-29. Its own Design section says "re-arms at 20 s", so the spec contradicts
    itself.
- **Why it matters.** AGENTS.md says docs never claim more than the code enforces. Billing is
  the promise the owner reads here, and "does not save minutes" understates it: Mute can add
  minutes.
- The implementer's hand-over note flags the re-arm as "the owner's call". This finding is that
  call, made explicit.

**Fix.** Code (preferred), test-first:

- Write `case (_, .mute): …; return [.muteMicrophone] + (isSoundOn ? handle(.speechEnded) : [])`.
- No grace is lost. A result is held only while `isSoundOn || isVoiceSpeaking`, and a result the
  voice holds gets its grace at `.assistantFinishedSpeaking`.
- Add a row: `live` (quiet), `.mute` → `[.muteMicrophone]`.
- Change `muteOnALineAResultOpenedKeepsTheFirstWordWait` to expect `[.muteMicrophone]`, so the
  first-word wait is not extended.
- Then the docs can say something true. For example: "an open line closes as if you had
  stopped speaking when you pressed Mute".

Docs only (if the owner keeps the re-arm): state the rule in all nine places. For example:
"Mute counts as the end of your speech: an open line closes after the usual silence, counted
from Mute, so a Mute can keep it open up to 20 s longer".

### CR-3 · Important · README.md:293, SECURITY.md:70-73, CHANGELOG.md:14-15, docs/roadmap.md: the indicator claim ships before it is checked, and the trail says "delivered"

**Problem.**

- **Every doc rests the privacy promise on the indicator.** README, its six translations,
  SECURITY.md and the CHANGELOG say "while muted LiveBridge holds no microphone, and macOS's
  microphone indicator shows it".
- **The code side is solid.** Every track is stopped (the table above).
- **The visible half is not verified.** That the indicator actually goes off for a `WKWebView`
  whose tracks all stopped is WebKit behaviour. The spec and the plan list it as a by-hand check
  (`docs/plans/2026-11-05-mute.md:312-316`, still `- [ ]`), and the implementer's hand-over says
  "pending the owner".
- **The trail says otherwise.** The spec's status and `docs/roadmap.md` already say
  "delivered".
- **It matters here.** If WebKit holds the capture device open after the last track stops (some
  engines keep it briefly, or until the context closes), the indicator stays on while the docs
  say otherwise.

**Fix.**

- Do the three by-hand checks before merge:
  - Mute → off; Unmute → on;
  - Start, then Mute at once, through the first-run prompt → stays off;
  - plug or unplug a headset while muted → stays off.
- Record the result in the plan's checklist.
- Until then, keep the spec and the roadmap entry as not plainly delivered.
- If the indicator lingers, word the docs by what is enforced ("LiveBridge stops every
  microphone track") and drop the indicator clause.

### CR-5 · Minor · README.md:325-326 and the six translations: "on a line already opening" says more audio is sent than is

### CR-6 · Minor · `AudioHost.swift:117-122`: a cancelled take still reports macOS's refusal

**Problem.** `mayTakeMicrophone` reports a refusal through `onEvent(.failed(problem))` before it
checks whether the take was cancelled.

- **New with this PR:** Unmute while the prompt shows, then Mute, then "Don't Allow". This ends
  a call the owner had just muted again.
- **Already the case for Start:** a Stop during the prompt, then "Don't Allow", runs
  `(_, .audioFailed)` on an off machine and shows the denied banner after the owner stopped.

Both fail closed, so this is no privacy issue, only a surprising end.

**Fix.** Report the refusal only for a take that is still current. CR-1's Bridge-side version
gets this for free: it re-checks the machine before acting on the problem. Write the test first.

## simplify

Report only. Each finding names the simpler form; none changes behaviour. Considered and not
taken are at the end.

### SI-1 · Minor · Simplification · `microphone.js:34-55, 70-75`: API that only the tests use

**Problem.**

- `attach()` returns a boolean and `unmute()` returns `true` or `attach()`'s result.
  `audio.js:138, 158` discards both, and the comment at `audio.js:137` ("False when muted")
  describes a value nobody reads.
- `deviceChanged` is exported only for `microphone.test.mjs`.

**Fix.** Return nothing, and drop `deviceChanged` from the returned object. The tests already
assert the outcome (`got.stopped`, `everConnected`, `pending.length`). They can fire a device
change through the real path, `watched.at(-1)()`.

### SI-2 · Minor · Simplification · `StatusPresentation.swift:36-39, 68-93`: derivable state and a two-pass headline

**Problem.**

- `isMuted` is stored beside `muteAction`, and `muteAction == .unmute` is exactly
  `isMuted && call != .off`. Its only reader is `MenuContent.swift:97`.
- The headline is computed as `(phaseHeadline, phaseDetail)` and then overridden by a second
  `switch (s.call, s.isMuted)`.

**Fix.**

- Drop the stored `isMuted`, and read `muteAction == .unmute` in `MenuContent`.
- Fold `case .listening where s.isMuted` into the first switch, and append `" · muted"` once
  for connecting and live.

### SI-3 · Minor · Reuse · `AudioHost.swift:63-65, 77-79, 87-89`: one `do/catch` copied three times

**Problem.** `startListening`, `muteMicrophone` and `unmuteMicrophone` each wrap
`call(...)` in the same `catch`, which reports `"The audio page did not <verb>: …"`.

**Fix.** One private helper, for example `perform(_ js:, failing verb:)`. With CR-1, the three
methods become one line each.

### SI-4 · Minor · Simplification · `microphone.js:20-31, 64-81`: `mute` and `release` differ by one boolean

**Problem.** Both run `token++`, set `muted` and call `letGo()`, and `letGo` is `drop()` plus
`watchDevices(null)`.

**Fix.** Use `function letGo(stayMuted) { token++; muted = stayMuted; drop(); watchDevices(null); }`,
with `mute() { if (!muted) letGo(true) }` and `release() { letGo(false) }`.

### SI-5 · Minor · Simplification · `audio.js:103-107`: a message nobody sees

**Problem.** `micLate` builds `'The microphone did not start in time.'`, but `microphoneFailure`
picks the sentence by `error.name`. The text is never shown, yet it reads like user-facing copy.

**Fix.** `Object.assign(new Error(), { name: 'MicTimeoutError' })`.

### SI-6 · Minor · Reuse · `band.tsx:11`, `register.tsx:558-559`, `MenuContent.swift:48-49`: pairs that differ only by a word

**Problem.**

- `BandActions` gains `mute()` and `unmute()`, each `link?.call('<action>')`, as `stop` is.
- `muteActionTitle` repeats `actionTitle`'s `map { $0 == X ? "…" : "…" }`.

**Fix.**

- Use `BandActions = { start(); call(action: 'stop' | 'mute' | 'unmute'); target() }`.
- Give `CallAction` a `title` (Start, Stop, Mute, Unmute) that both card titles read.

### SI-7 · Minor · Simplification · `audio.js:148`: a third "already muted?" check

**Problem.** The machine never sends two Mutes in a row (`CallMachine.swift:163`), and
`mic.mute()` is idempotent (`microphone.js:65`). The early return in `audio.js` `mute()` guards
a case that cannot arrive.

**Fix.** Drop it. A repeated call would at worst reset an already-fresh detector and post
`level` 0 again.

### Simplify findings considered and not taken

- **One counter instead of `stops` and `mutes`** (reuse lens): not taken. Start must ignore a
  Mute while Unmute must not, so one counter cannot express it. CR-1 removes both instead.
- **Unmute replies before the microphone is back** (efficiency lens): not taken. The spec
  accepts the wait ("may still show Muted"), and it shows Muted for longer, which is the safe
  direction.
- **Stop the `ScriptProcessor` while muted** (efficiency lens): not taken. The muted branch is
  already cheaper than the unmuted one, and a result can open a line that needs the running
  graph.
- **Collapse `CallEvent`/`CallEffect`/`AudioSide` mute pairs into one `Bool` case**
  (simplification lens): not taken. Unmute asks macOS first and Mute does not, so the two
  branches really differ.

## security-review

**Scope and threat model.**

- Every process running as the owner can drive the socket (SECURITY.md).
- The audio page is bundled code under the app's own scheme.
- The risk here is LiveBridge's own code breaking the promise Mute makes, not an attacker.

**Result: no finding reached the skill's 8/10 bar, so none is reported.** No candidate scored
≥ 7, so nothing went to the false-positive filter.

**Candidates refuted:**

- **Script injection through `callAsyncJavaScript`.** The new calls `"LB.mute()"` and
  `"return await LB.unmute()"` are fixed strings. Request data never reaches the page.
- **`mute`/`unmute` on the wire.** They decode into a closed enum (`CallAction`), so an unknown
  value is a 400. Unmute gives a local process nothing it lacked, since it can already Start a
  call. SECURITY.md:69-73 says so.
- **Mute/Unmute while off.** `(.off, _)` drops them (`CallMachine.swift:158`).
- **Prototype keys in `microphoneFailure`.** The lookup uses `Object.hasOwn`
  (`microphone.js:100`).
- **A band showing a false Muted.** It draws the marker only for `isMuted === true`, and the
  button only when the field is present (`band.tsx:55, 70`). An older app shows no Mute, never a
  wrong one.
- **Two `attach()` calls at once** (a device change racing Unmute, or `onended` and
  `ondevicechange` together). The later success `drop()`s the earlier, so one capture remains.
- **The milliseconds between `isMuted = true` and `LB.mute()` arriving.** A device change in that
  window can take the microphone, but the token bump that follows releases it. A theoretical
  race.
- **A permission revoked while muted.** Unmute asks macOS first and reports a refusal. The
  page's `NotAllowedError` ends the call.
- **Every microphone path in the table above.** Each was traced and refuted, except the
  untested native window in CR-1, which is correct as written.

## Declined to judge

- **A `callAsyncJavaScript("LB.mute()")` that hangs rather than throws** (a hung WebContent
  process): this is a WebKit failure mode, and the process-termination path covers the
  realistic case.
- **Strict FIFO between Swift actor jobs and MainActor jobs** across the HTTP and menu tasks:
  relied on, not proven.
- **A muted mark in the menu bar glyph, a hotkey, `/live mute`, or `/live status` naming the
  mute:** out of the spec's "Where".
- **Button order and styling** in the band and the card: layout taste.
- **Any local process can unmute:** documented as not a control.
