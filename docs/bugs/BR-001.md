- **Found:** 2026-11-04
- **Where:** `app/Sources/BridgeCore/Codex/VoicePrompt.swift`, `VoicePrompt.text` (the paragraph
  that starts "A handoff is the only way anything reaches Claude"), which is the only thing that
  makes the voice hand off; `RealtimeSession.handoff(_:)` in
  `app/Sources/BridgeCore/Codex/RealtimeSession.swift` is the only path a request takes to
  Claude, and nothing in the app notices a turn that should have taken it and did not.

The owner asks for something, the voice answers "Looking now" or "I'll take a look", and no
`handoff_request` item arrives. Nothing reaches the Claude Code session, the line waits for a
result that will never come, and the owner is told nothing. The Conversation submenu shows no
"Task" line for that request, which is the only trace. ADR 0001 item (b) measured this at 3 of 6
smoke runs before the prompt rule and 0 of 5 after it (commit 20649ff, 2026-11-02).

The probe recorded in ADR 0001 item (n) (2026-11-04, `codex-cli 0.166.0`, debug app with
`--fake-mic` saying "Please list the files in this folder", the smoke test's fake session) saw it
again. Each run had its own home directory (`/tmp/lbprobe.*/home`), so each first line opened
with the current prompt, no owner prompt (`settings.json`: `"prompt":""`), `autoContext` off and
no seeded conversation. Run 1 opened no line. Of the 10 lines that opened, 3 promised a look and
handed nothing off. The saved `continuity.json` of each failed run holds only these two lines,
with no `handoff` line, while every other run has a `handoff` line before the owner's:

```text
run 3   owner : Please list the files in this folder
        voice : On it — I'll check that folder.
run 8   owner : Please list the files in this folder
        voice : Looking now.
run 9   owner : Please list the files in this folder
        voice : I'll take a look.
run 5   handoff : Please list the files in this folder
        owner : Please list the files in this folder
        voice : Sure, I'll check that folder now.
        claude : [RESULT] Example session: There are three files in this folder: alpha.txt, ...
```

(Read on 2026-11-04 with a script that prints each line's speaker and text from
`home/Library/Application Support/LiveBridge/continuity.json`; the `/tmp` directories are not
kept.)

The model did not delegate; codex and the app dropped nothing. codex traces every frame the
realtime websocket receives in its log database (`~/.codex/logs_2.sqlite`, target
`codex_api::realtime_websocket::wire`; in run 3 all 247 frames from the first one kept
have a wire line). The database keeps about 6 MB of rows per codex process and prunes the
rest. In the successful runs that pruned the first line's early seconds, handoff included. In the
three failed runs, which closed after one line, the record is unbroken from mid-request (runs 8
and 9: from the request's `input_transcript.added`, 1.4 s before its `turn.done`) or from 0.3 s
before the request's `turn.done` (run 3), to the line's close 20 s later. It holds the owner's
turn, the voice's turn and nothing else: no `delegation.created` frame and no codex
`thread/realtime/itemAdded`. Run 3, from that database:

```text
{"type":"turn.done","turn":{...,"end_ms":3600,"role":"user","start_ms":1200,"transcript":"Please list the files in this folder"}}
{"type":"turn.created","turn":{...,"end_ms":3600,"role":"assistant","start_ms":3400,"transcript":" On it"}}
{"type":"turn.done","turn":{...,"end_ms":6800,"role":"assistant","start_ms":3400,"transcript":" On it — I'll check that folder."}}
app-server request: thread/realtime/stop
```

In all three the voice's turn began 200 ms before the owner's turn ended (3400 against 3600 ms
in runs 3 and 8, 3200 against 3400 ms in run 9): the voice started speaking before the request
was complete. The probe's successful runs cannot show whether they differ, because their early rows
were pruned; the measurement below shows they do not.

The rule is as it was written. `git log -p` of `VoicePrompt.swift` since 20649ff shows one change,
8ca5b24 (2026-11-02), which added the `[ASKING]` tag and a closing paragraph about Claude's
questions. That paragraph tells the voice to talk an `[ASKING]` question through "without handing
off" and to "hand off only the owner's reply". No other part of the session's start changed in a
way that reaches the model: the realtime model was the default in both measurements (the Settings
field that could change it was removed in a5f59df), and the same realtime options are sent.

A measurement on 2026-11-04 settles the two readings this entry first offered. Each run was a
debug build from a fresh home, saying the same request with `--fake-mic`, with one line that the
script closed 6 s after the voice answered. A is the prompt above. B rewords only the handoff
paragraph the way the owner framed the rule: handing off is the only thing the voice can do,
answering from what it already has needs no handoff, and it must never say it is doing or checking
something unless it hands off in the same turn. The runs alternated A and B, and each was read
from codex's wire log right after it ended:

| | Lines | `delegation.created` | Promised a look, no handoff |
|---|---|---|---|
| A, the rule since 20649ff | 20 | 17 | 3 ("Sure, I'll take a look.", "On it—I'll pull up that folder's contents now.", "On it, checking that folder now.") |
| B, the owner's framing | 20 | 18 | 2 ("On it—I'll check.", "Looking now.") |

- With the current rule the rate is 3 of 20 here and 3 of 10 in the probe: about one request in
  five. The 0 of 5 measured after the rule was luck, so the rule never closed the failure; it
  lowered it from about one in two.
- Rewording the rule did not move it: 2 of 20 against 3 of 20 is chance. More prompt work is
  unlikely to close it.
- The early start is not the cause. The voice began 200 ms before the owner's turn ended in 14
  of 17 delegated A runs and 16 of 18 delegated B runs, as often as in the failures.
- The 40 runs kept a line open 550 s in all, about $0.46; one `scripts/smoke.sh` run with B
  (passed, 62 s) checked that small talk still makes no handoff.

**Suggested fix:** a hypothesis. A model instruction is not a control, and the measurement shows
wording does not reach zero, so the fix has to let the owner notice a missing handoff. The app
cannot tell a promise from an answer by its words: the voice speaks the owner's language, and
matching phrases in every language is not a fix. So the signal has to be positive, from the
event itself, not a guess about the words. The smallest such change: the app confirms every
`handoff_request` it receives where the owner hears it, a short sound into the line or the
band's state, so "On it" without that sound tells the owner nothing was sent. Alternatives
considered: a second model judging each reply without a handoff (language-independent, but
another detector to trust, with its own latency and cost), and handing off every owner turn and
letting Claude decide (against the design: the voice answers what it already knows by itself).

What must not change with it: the voice still answers from what it already has without a handoff,
hands each request off once (the `handoff_id` de-duplication), and asks "yes?" before anything
destructive or outward; the app still never answers a Claude Code permission prompt.

**What this evidence does not establish:** whether the rate depends on the request, the language
or the voice: every run used one English request in a synthetic `say` voice. It does not show how
often B, which allows answering without a handoff, keeps a request that needs Claude from
reaching it in other wordings; the runs used only one request and the smoke test's small talk.
And it does not show that a confirmation sound is enough for the owner to notice; that is a
design question for the owner.
