- **Found:** 2026-11-06
- **Where:** `app/Sources/BridgeCore/Call/Continuity.swift`, `Conversation.SummaryAsk` and the
  `isStale` bit; `app/Sources/BridgeCore/Call/SummaryAsks.swift`, `ask`, `answer` and
  `Policy.answerable`; `app/Sources/BridgeCore/Bridge.swift`, `context(_:)`;
  `plugin/hooks/register.tsx`, `contextAsked`; `ContextBody` in `Wire.swift` and `plugin/hooks/wire.ts`.

`POST /v1/context` says nothing about when its summary was written. The app has to work out which
ask a summary answers from an open ask, its age and whether a gap came after it, and a summary
nobody asked for (`/live context`) cannot be dated at all. Each wrong guess costs one of two things:
a summary that does not cover a gap is taken, or a good one is dropped.

Run at 9f50f03 with the review's probes (`swift test --filter`, output as printed):

```text
PROBE n1 outOfSync nil needs false context Optional("[CONTEXT] Alpha: Written before the private thing.")
PROBE n2 Optional("[CONTEXT] Alpha: Everything from before.")
PROBE n3 context nil needs true
✘ Test probeASecondAskPastTheFirstsLifeStillCounts() recorded an issue: Expectation failed: !taken
✘ Test probeASummaryForAPressAfterTheGapCounts() recorded an issue: Expectation failed: taken
```

- **n1.** With the pause on and the call off, the owner types during their own `/live context`.
  The turn is refused, the summary is taken and clears *paused*, and the voice is told it is
  current though the summary may hold the paused text. A later line of that turn marks *paused*
  again, so the mark stays cleared only if the turn's last line lands before the summary. The spec
  accepts this as a 60 s window on an explicit command.
- **n2.** A `/live context` crossing New conversation brings back what was forgotten.
- **n3.** An ask lives 120 s and the mod gives up at 60 s. Ask, gap, the mod drops its send, press
  again at 70 s: the fresh summary is ignored, a model call is spent, the menu says Loading until it
  times out, and `/live context` says "Sent a summary" for one the app dropped.
- **Second ask.** Asks at 0 s and 100 s, a gap at 125 s, a summary at 130 s: it is taken, though it
  was asked for before the gap, since the second ask kept the first one's clock and the stale bit
  lands on it either way.

**Suggested fix:** a hypothesis. The app puts a generation in what the mod reads, bumped at each gap
and forget, and the mod echoes in `ContextBody` the value it read when it started writing. That
dates `/live context` too, and `SummaryAsk`, `Policy.answerable` and the stale bit go, about 35 lines. The
field is optional, so it can come in any release. What must not change: a mod that sends no
generation, and every released one, is treated as today, and a wire change touches `Wire.swift`,
`plugin/hooks/wire.ts` and `wire/fixtures/` together. The alternative is to keep the guess and give a
second ask its own clock, which fixes n3 and the second ask but neither n1 nor n2.

**Update, 2026-11-07, from PR 53's review.** The mod drops `/live context` in 0.4.2, which changes
the route above; the table below still shows the route as it was. This was read from the code, not run.

- **The generation no longer closes n1 and n2.** They now need a mod that has `/live context`, and
  those mods send no generation and must be treated as today. Only the app refusing a summary with no
  open ask closes them, and that ends `/live context` for those mods.
- **A summary with no open ask can still come from the current mod.** A second ask that comes after a
  poll took the first and before that summary lands keeps the first ask (`SummaryAsks.ask`), that
  summary closes it (`SummaryAsks.answer`), and the reply to the second finds none open and is taken. A
  press and a line opening each ask; the menu alone refuses a second press while one is pending.
- **n3 and the second ask stand**, as they are about the app's asks. The "Sent a summary" clause of
  n3 stays true on older mods.

**Suggested fix, as of this update:** a hypothesis. Have `SummaryAsks.answer` refuse a post when no ask is
open. What must not change: a summary that answers an open ask is taken as today. The reply to a
second ask would be refused too; the summary before it was taken and answered any press, so that
costs a fresher summary at most. The alternative is to keep taking such a summary until no supported mod has `/live context`, with
SECURITY.md's residual risk standing until then. The generation stays a hypothesis for n3 and the
second ask.

**What this update does not establish:** how many sessions still run a mod with `/live context`, and
how often a reply to a second ask lands with none open; neither was measured.

**Update, 2026-11-12, from the summary-model work.** For a current app with a current mod, a
number replaces the guess. Each ask that names a model carries the next number (`Work.context.ask`), and a
second ask that joins an open, current ask keeps that ask's number; the mod echoes the number of
the ask it wrote for (`ContextBody.ask`), and `Bridge.context(_:)` takes a post only when the number
is the open ask's. A post with another number is reported stale and leaves the open ask open. That
closes n3 and the second ask for that pair, tested with `aStalePostDoesNotAnswerTheFreshAsk`,
`aJoinedAskKeepsItsNumber` and the mod's `theSummaryEchoesItsAsk`. An older app or an older mod
sends no number, and its posts keep the guess (`anOlderModsPostAfterAForgetAndASecondAskIsRefused`), so n1, n2,
n3 and the second ask stand for those pairs, and the status stays open.

**What this evidence does not establish:** every run above is a test on a fake mod or a direct call,
at the app's boundary; none of it came from a real summary or a real model. How often a summary
crosses a gap in real use is unmeasured, so the cost of leaving this open is an estimate.
